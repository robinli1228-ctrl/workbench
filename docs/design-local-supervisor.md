# Project Supervisor and Multi-Repository Setup

Status: implemented in the current code; see [ARCHITECTURE](ARCHITECTURE.md) for the exact behavior.

Creating a project means choosing a connected device, a logged-in and adapted CLI, and an actual model. The supervisor can run on a local machine or on a server, and the execution location is never guessed from where the Home runs. Each device sets a default root directory once and each project sets a stable folder name; the project directory on a newly added device is made of the two. Directories of old projects are not moved and historical runs are not rewritten.

A project owns multiple repositories. When a repository is associated, a long-lived baseline worktree is created in the project directory on every participating device: `.worktrees/project-baseline/<repository key>`, on the branch `agentwb/<project ID>`. The first baseline takes a fixed commit from the specified remote source branch, and a full starting SHA can also be given. By default the project collaboration branch is published to the remote; a purely read-only reference repository can opt out in project settings. Devices that join later must align to the same commit. The original clone is never switched to another branch or overwritten, and the repository path of a new role points to the project baseline. An empty project without a Git repository first gets a project directory, and the baseline is created as soon as the first repository is associated. A role only chooses the project, device, CLI, model and prompt. A run fixes all repositories of the project and the device paths. Cross-device delivery advances the project collaboration branch with a fixed SHA, and merging into the main line is a separate operation.

A project message without an `@`, or an `@supervisor`, goes to the configured supervisor. Explicit worker roles are executed under the original scheduling, and `@all` stays an announcement. The supervisor reads context from a limited number of recent conversation items and the platform catalog, queries with `wb setup catalog` and submits structured actions with `wb setup propose`. Actions include registering or cloning and binding repositories, and creating or editing worker roles. The web page lists the actual parameters and executes after confirmation; the agent tool allow-list offers no approval interface. The actual operations are performed by the target Worker, and the results return to the group chat and are read by the supervisor on the next turn.

The CLI and the Worker communicate through temporary request and response files inside the workspace of the current turn, and only the Worker accesses the Home, so the Codex sandbox does not need network access. The Worker fixes the run identity, restricts the callable interfaces and cleans the temporary files at the end. Codex receives the `wb` context explicitly through the config of the current `thread/start` and is compatible with `inherit=core`, without changing global configuration. The tool allow-list of a trusted single-user environment is not described as complete isolation against an arbitrary shell on the same account.

Project settings manage the description, folder, repositories and supervisor in one place. Associating an existing directory sits in a collapsed area, and role editing only offers an entry that leads to project settings. Repository preparation only clones into a source directory that does not exist, or checks an existing directory whose origin matches, and then creates the project baseline worktree. Fast-forwarding the baseline requires a clean directory and reachable commits. A fixed-version delivery across devices goes through the existing confirmation flow and pushes to a separate delivery ref and the project collaboration branch. The base settings store GitHub/Gitee accounts and can create private repositories by default. After a timeout the creation is not blindly repeated; the existing repository is checked and then associated.

The base settings add device registration, SSH checks, Worker installation and a default workspace. The configuration assistant uses a fixed prompt and a logged-in CLI, queries the actual state and proposes action cards, which run only after user confirmation. Secrets are entered in credential forms and never enter the model conversation. Onboarding currently requires Node.js 22.16+, npm and Git on the remote machine. The background Worker restarts its child process automatically but does not yet install a system boot service. Installation success and the Worker actually coming online are shown separately.

Account authentication and remote repository creation require a user-provided token for acceptance and cannot be replaced by simulated tests.
