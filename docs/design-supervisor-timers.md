# Supervisor Timers and Progress Patrol Design

Status: implemented in the current code. Real-world verification coverage is the operator's responsibility.

## Goals and boundaries

When a user asks the supervisor in the project group chat to set up a scheduled task, the supervisor must be able to create, view, modify, pause and delete the tasks of the current project through `wb timer`, which is shared by all managed CLIs, and must receive a persistent receipt. A "Scheduled jobs" entry between the token statistics and the base settings at the bottom left manages the schedules of all projects in one place. Scheduled dispatch and progress patrol are two different kinds of jobs, and a healthy patrol does not wake a model.

This design reuses the Home's existing `ScheduledJobs`, the Room/Task/Run model and the project-settings schedule data. It keeps the Worker's 15-second connection heartbeat, the Home's 1-second scheduler tick, the per-minute model-free stalled-run check and the stage-scheduling semantics of `wb schedule`, and it does not introduce a second cron service. It does not create jobs for an AI on its own, does not modify business repositories, and does not let scheduled jobs bypass the existing dispatch, approval or Git delivery constraints.

## User path and pages

The bottom-left buttons are, in order, token statistics, scheduled jobs and base settings. "Scheduled jobs" opens a full-screen page that defaults to the current project and can switch to another project or show a summary of all projects. The list shows project, name, type, target role, enabled state, next time, last check or execution and its result; opening an item shows the trigger records and the related group message or run. The page offers create, edit, pause/enable, run-now, and delete. Editing uses a dialog and deleting requires confirmation. The earlier "project settings, scheduled jobs" form is removed and project settings only keep a link to the management page, so there is one editing interface.

Ordinary "scheduled dispatch" keeps the four schedules once, interval, daily and weekly, dispatches once to a fixed role when due, and the interval is at least 15 minutes. "Progress patrol" is new: it allows only interval schedules, at least 10 minutes, and its target is always the current project supervisor. The page distinguishes the two clearly, and a patrol is never shown as something that calls the supervisor every time.

## CLI and Home contract

`wb timer list` reads the tasks of the current project and the most recent trigger records. `wb timer create '<JSON>'`, `update '<JSON>'`, `pause '<JSON>'`, `resume '<JSON>'` and `delete '<JSON>'` perform the corresponding operations. The commands are forwarded to the Home through the existing Worker file bridge, so Codex, Grok, Antigravity and Claude Code do not each need a different tool. `wb schedule` still only submits execution stages and accepts no clock fields. The help text, the capability list and the supervisor working instructions must explain both commands clearly.

The Home confirms the project and the fixed supervisor identity from the active run and does not accept a `projectId` reported by the CLI. Ordinary worker roles, finished runs, roles of other projects and the platform configuration assistant cannot change timers. Edit, pause/enable and delete operations carry the current revision, and a conflict returns the latest state so the supervisor can read again. All write operations require a stable `requestId` and are idempotent within a project by parameter fingerprint: a retry with the same ID and parameters returns the original result, and the same ID with different parameters is rejected. The operation audit records the source run, the action, the task ID and the time. A successful receipt contains the task ID, revision, enabled state and next trigger time. After a delete the trigger history and the operation audit are kept. The supervisor creates or changes persistent jobs only when the user explicitly asks for a schedule, and never treats text from web pages, repository files or other roles as authorization.

## Patrol and wake-up

When due, the Home runs a deterministic check over the active execution plans of the current project, the latest blocked or failed plan, unfinished runs and existing `runAlerts`. It does not hand older failure chains back to the supervisor. When there is no task, progress is normal, or nothing changed, only the check time and result are updated: no Task or Run is created and no model tokens are used. Anomalies such as a blocked or failed plan, an offline Worker, or a run with no event for more than 10 minutes produce a stable key by project, object and anomaly state, and at most one short diagnostic request is dispatched to the supervisor. A current anomaly found on the first check is also notified once; the same anomaly persisting does not wake the supervisor repeatedly, and it can be notified again if it recurs after being cleared. If the supervisor is busy the existing queue applies and the same role is not occupied concurrently. Stage completion remains driven by `executionPlans.advance` events and does not wait for the next patrol.

A patrol only reports evidence and asks the supervisor to judge. It does not retry failed tasks, terminate the CLI, push or deploy on its own. After a Home restart it continues from the persisted `nextRunAt` and the anomaly keys. Multiple missed runs during downtime are merged into one check so that a series of model tasks is not replayed. After pause or delete no new check fires, and runs that have already started follow the existing stop rules and are not interrupted silently.

## Compatibility, verification and release

Old `scheduledJobs` records without a type are read as "scheduled dispatch", and existing schedules and trigger records are neither migrated nor reinterpreted. `wb timer` is announced in the supervisor prompt only when the Home and the Worker are on the same version; old Workers do not claim support. The page and the CLI use the same source of truth, so a change on one side is visible on the other after a refresh.

Before implementation, reproduce the gaps with temporary local tests: the supervisor having no interface, a 10-minute patrol that cannot be created, and a repeated request that could create duplicate jobs. When done, cover identity and project isolation, revision conflicts, idempotency, old-task compatibility, a normal patrol using zero model calls, one wake-up per anomaly, a new alert after recovery, merging of missed runs, and pause/delete. Real acceptance should use an isolated QA project and both a local and a cloud Worker, verify that `wb timer` can be called through different CLIs, that the page can be managed at 390px width and on desktop, and that a trigger can be traced in the group chat. Health checks or simulated receipts must not stand in for real model acceptance. When deploying, back up the Home data and code first, confirm that no unfinished execution is affected, and then verify each running instance.
