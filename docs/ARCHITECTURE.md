# Current Implementation Architecture

Local development adds independent native Agent switching through `native-agent-switch.mjs`, `native-agent-switch-worker.mjs` and `native-agent-context.mjs`. Home persists conversation/segment association and an idempotent operation; Worker reuses native terminal creation and exact process ownership before publishing a successor. Historical segments remain read-only. A versioned delivery receipt binds the bounded factual context to the target's first accepted input. Binary vendor histories use the verified creation directory and original Home page-turn records where native text is unavailable. No vendor transcript conversion, second scheduler, cross-device migration or deployment is included; see [design](design-native-agent-switch.md) and [implementation plan](plan-native-agent-switch.md).

This document describes the code as it is. Product scope is defined by the [PRD](PRD.md). Capabilities that are only planned are listed under "Current limitations" and in the design documents, never here as features.

Manual device tunnel recovery uses `POST /api/devices/:id/reconnect` and a read-only `GET` progress endpoint. Home temporarily fences admission for that node, refuses pending/active Runs, native turns, terminals, retained CLIs, role switches and outstanding queries, then runs the read-only Linux ownership/activity probe in `src/device-reconnect.mjs` through a separate SSH connection. Unknown Worker identity, unreadable records, active child processes and changed device bindings fail closed. Only the Home-owned reverse-tunnel child receives SIGTERM; its exit is awaited without force-killing. Services and desktop forwards remain untouched. Success requires a different Worker socket with a new heartbeat. The progress record is bounded and process-local; a Home restart is not proof of recovery. No automatic network-repair loop is added.

Source-sync observation uses ephemeral metadata/hash caches. Complete watcher coverage retains five-minute metadata reconciliation and an hourly full-content check; degraded coverage retains the thirty-second/five-minute fallback. Known file events reread affected files; ambiguous events traverse metadata. Native directory watchers share one process budget: 128 on macOS and 4096 elsewhere. EMFILE/ENOSPC pauses new allocations for ten minutes while existing watchers and fallback sweeps continue. Transfer byte verification, apply fences and histories remain intact. Observation captures yield under task load without waiting indefinitely. Receipt polling starts from pending receipts. The safety contract is maintained in [design-source-sync](design-source-sync.md#136-observed-implementation-boundary); code capability does not imply deployment.

Idle observation batches rest 10 ms after each 32 entries/files; busy file checks keep the existing eight-file/25-ms pacing. Manifest validation still runs in full after yielding. Due periodic scopes are staggered by 250 ms idle or 1000 ms busy, with at most five seconds of inter-scope rests per tick. Closing or replacing a scope cancels at batch boundaries, and publication still rechecks the complete configuration. Explicit transfers retain independent byte verification and do not reuse observation hashes.

Home's minute progress inspection reads active Runs through the existing partial index and checks only open alerts; terminal history remains stored. Workspace polling retains four project summary sets and sixteen project/conversation cursor scopes. Relevant Store writes invalidate summaries, while direct SQL, external connections and rollbacks invalidate conservatively; unknown or active transaction state disables reuse. Online status, language, permissions and nonhistorical page fields are evaluated on each request. The feed reuses unchanged normalized history and field digests instead of rebuilding and hashing all historical JSON. These caches serve the UI only: scheduling and detail reads continue to read SQLite, and process restart discards the caches.

The supervisor chooses its own implementation methods and pursues missing capabilities through terminal tools, teammates or tool development before resuming the original task. It can handle authorized local work directly. Explicit user authorization may extend the instruction scope beyond the default workspace; actual runtime permissions remain enforced and require access to the specified target or an execution environment with that access. A prompt change does not expand Codex writable roots automatically. Exact previous built-in supervisor prompts follow updated defaults in either language, while custom prompts remain unchanged.

Explicit native-session sends and steers query `native_takeover_state` through the existing Worker channel. The response binds the lease, runtime and session to PID-identity verification and the Runner’s active-turn/resident state. Home applies it only if the captured takeover, lease and active turns have not changed while awaiting the response. Verified exit releases ownership; a retained process can reopen a falsely retiring takeover and settle absent old active turns. Closing, paused, unknown and unmatched states never authorize a duplicate launch. Preparation failures before resident attachment preserve the existing idle process report. This adds no polling or automatic retry of failed input.

## Runtime structure

### Optional independent remote access

`modules/remote-access/` packages the separate loopback gateway, password/session store, local administration service and dedicated SSH tunnel lifecycle. It is not started by importing Home and does not share the task scheduler. `src/remote-access-settings.mjs` bridges only a fixed local administration allow-list; its private configuration path comes from `REMOTE_ACCESS_CONFIG` or `DATA_DIR/remote-access/config.json`. The Basic Settings card in `public/remote-access-settings.js` fetches status on entry/actions only, patches explicitly changed fields and preserves hidden values and drafts.

Home API authentication is still required. Relay administration additionally requires exact local Host/Origin, a loopback peer and a fifteen-minute HttpOnly SameSite=Strict proof cookie scoped to `/api/settings/remote-access`. Proofs are bounded to 64 and pruned on requests. They are not returned in JSON. The older standalone gateway strips Cookie and Set-Cookie, so it cannot acquire/forward the proof; the packaged gateway also rejects this management prefix. Public browser login remains a separate fixed fifteen-day session. Private credentials/paths are excluded from management status, general state and browser storage. Missing services fail closed without spawning replacements. See [the contract](design-remote-access-settings.md).

Release provenance includes `modules/remote-access` alongside the existing runtime paths, detecting added, changed and missing module files. Packaging the optional module does not update or restart a running independent gateway or Worker.

Server-field edits require the local service's `configPatch: 1` capability. Home and the recovery UI send changed fields to `/api/config-patch`; validation and read/merge/write happen in the service's shared lifecycle queue, preventing a delayed Home save from overwriting a recovery-page update. Old services expose a read-only configuration card with an explicit upgrade notice; there is no full-snapshot save fallback. Existing password and enable/disable operations retain their compatibility.

Group-conversation branching and team copying are entered from two non-submit buttons in the Project actions card of the project's basic settings. Branching captures the selected project/chat before opening the existing title form; copying opens the existing configuration preview. The main toolbar and sidebar no longer expose the separate group-actions menu. Opening either action does not save the settings form; successful creation navigates to the created chat/project.

Role cards separate current execution/availability from historical outcomes. Active or unsettled Runs and pending collaboration take precedence; idle roles use fresh device/CLI/model checks, with stale evidence shown as requiring a check. The latest failed task is a separate history link, including admission failures without a Run. Refreshing availability never rewrites Run status or report verdicts. This is a browser projection, not model-inference verification or automatic task recovery.

The waiting queue owns the displayed IDs of chat-origin tasks that are ready and have no current Run, plus steering tasks still awaiting input acceptance or blocked before acceptance. Chat rendering consults that same membership before creating an Agent placeholder or its controls, instead of applying a second queue predicate. Their source messages stay in the chat, labelled Queued. Queued CLI recovery actions live on the queue item; source messages, completed replies and already-executed collaboration waits remain in the chat. Queue items show one text line; secondary waiting/timeout explanations are not rendered. Open waits (`queuedWaits`) are listed in the same queue at the slot where the wait began; they hold nothing back, their wake inherits the slot (`queueOrder`), and they can be dragged like messages through `/queue/order` (`wait:<requestId>` items). Queue rendering stays stable during a drag, then reconciles both views on release, without additional polling.

`Rooms.editQueuedMessage` recalls a human message and all of its still-ready recipients in one transaction, cancelling only those queued tasks and their request records through the existing cancellation path. It rejects running, coordinated, scheduled and steering work; originals are never rewritten. The browser persists a command identity before recall, blocks sending while the outcome is unknown, and retries the same recall after a lost response. A successful recall restores the original text, attachments and reply reference into an empty composer; only a later explicit send makes a new queued message. A nonempty draft is never overwritten. This does not change admission or occupancy checks.

`cli-session-recovery.mjs` binds native drivers to PID/start/user and project/role/native-session proofs. Home's `cli-session-recovery-home.mjs` checks the existing task before admission and keeps unknown or busy occupancy queued. Ordinary occupancy probes run only after the other Room admission gates pass; each queue scan checks only the first task for an identical recovery target, without sharing task-bound results or stop consent. Accepted launches deferred by a final occupancy race still retry independently of those gates, and Worker launch-time checks remain fresh. The human-only recovery dialog rechecks the displayed snapshot, stops only verified driver/tool instances and resumes the existing native association. Managed POSIX drivers have dedicated process groups; unknown orphan members block, but do not authorize signals. A deferred launch reuses its command and Run; cancellation and final admission checks prevent reactivation and slot leaks. Warm retirement reports process exit separately from finished business results. New Home/Worker negotiate `cliRecovery:1`; old Home retains conservative occupancy rejection and ordinary warm reuse. See [recovery contract and measured coverage](design-cli-session-recovery.md).

`terminal-resume.mjs` also supplies the shared `recordedProcessState` and `managedRunProcessState` occupancy checks for CLI switching, native-history admission, terminal release, legacy driver admission and Worker restart reconciliation. Saved PID/start/user proofs distinguish `active`, `exited` and `unknown`; a changed startup cannot inherit a historical session lock. Legacy executable clues only exclude a recognizable foreign process, never authorize signals, while generic launchers or missing identity remain unknown. Recorded tool children remain part of occupancy. Finished reports and native history are not rewritten to clear a lock. These are on-demand checks at the existing entry points, not a new background scanner.

Five bilingual role templates describe responsibilities for planning, execution, review, testing and cross-device coordination. The first four execution prompts remain empty; `crossDevice` includes execution text, without enforcing a node binding or creating project roles automatically. Templates can be edited and restored, not deleted; a `deleted` record left by an older version no longer hides a built-in. Existing role definitions are not migrated; stable template keys remain separate from localized names. User-saved instructions are not bulk-edited. On the new `minimalInstructions:1` Home/Worker path, execution contains trusted role identity, configured instructions, the current task and necessary task events. Responsibility remains discovery data, not the owner's execution prompt. Exact previous maintained platform/supervisor defaults normalize to current bilingual defaults; custom values, including explicit empty values, remain unchanged. This path is released on compatible macOS and Linux Workers; optional saved-source synchronization is a separate capability and input contract. The isolated adapter-specific evidence and post-rollout acceptance limits are maintained in [the design](design-minimal-injection.md#11-observed-acceptance-boundary).

The CLI chooses whether and how to collaborate. Explicit user authorization may extend the instruction scope beyond the default workspace; actual runtime permissions remain enforced. A prompt change does not expand Codex writable roots automatically. Essential isolation boundaries and repositories outside the current directory remain disclosed; ordinary device and repository inventories are queried on demand.

The editable v2 defaults live in `minimal.platformTemplate` and `minimal.supervisorTemplate`. The platform template opens with the four cases that go to the user (tradeoffs that mean rework, permissions/accounts/spending, deleting others' work, publishing), lets each role choose whom to @ from `wb discuss peers` (responsibility, device, availability, token balance) with `wb ask` or `wb call`, and requires a goal, role/change boundary, exact device/version/file inputs and return evidence when assigning work. The long review, cross-device sync and error-code guidance moved out of the template into `wb help review`, `wb help sync` and `wb help errors`. The supervisor template keeps the supervisor out of code (it assigns even small tasks, answering questions excepted), routes unaddressed messages by the same peers signals, and covers independent review/testing, acceptance, follow-up, bounded retries and replacement, approval-controlled configuration/delivery. These are execution instructions, not new scheduler, retry or authorization mechanisms. Legacy minimal boilerplate remains recognizable but is not injected; the current templates are sent as configured components. Exact previous built-in defaults follow the update; custom and explicitly empty values remain unchanged unless the operator edits them. The four work-role presets remain responsibility-only; the cross-device preset explicitly includes execution text. Changes apply at next-turn admission without resetting native history or changing running turns.

The cross-device prompt revision distinguishes opt-in scoped saved-file synchronization (which can include uncommitted edits) from approved fixed-commit delivery for formal review and acceptance. It does not promise universal synchronization or a transfer deadline, treat project-level status as per-file evidence, or treat peer discovery as a file lock. File ownership must be coordinated. Explicit quick checks and informal reviews identify actual paths, devices, observation times and byte hashes, with input rechecks; they do not establish fixed-version acceptance. Local development still commits completed work. Shareable evidence belongs in authorized synchronized bound-project documentation, not solely in an isolated worktree; private independent-review material remains guarded. These are prompt/preset changes only, not a new path-status API, output availability classifier, handoff copy or sync policy activation. Existing role instructions are not bulk-replaced.

### Managed input language

The sidebar mode selector uses text-only Group chats / Sessions buttons with a blue active underline lying on the full-width gray divider and left/right keyboard switching. It shares the existing native-session mode transition and binds a single-chat-bubble plus icon to the currently selected mode. Project rows use unboxed outline icons; selected group-chat and session rows keep the ordinary row surface and border, distinguished by an accent title and icon, and the selected native row carries `aria-current`. These frontend styles leave footer controls, native-session behavior and backend routing unchanged.

The workspace state projection includes a compact cross-project `sidebarExecutions` list, containing only execution IDs, project associations and device/runtime/native-session identities. It derives activity from online managed Runs and active page-takeover turns; native turn metadata is selected without loading event bodies. Both sidebar lists use the same 14px SVG-mask hourglass, rotating through CSS once every six seconds and static under reduced motion, independent of selection styling. Leading project glyphs grow from 22px to 25.3px and native Agent marks from 26px to 29.9px. Fixed status space prevents title overlap; the collapsed rail places the hourglass below the enlarged mark. Native rows match the exact device/runtime/native ID, including older expanded histories, and reuse existing state refreshes without additional catalogue reads or model calls. This is presentation only: no scheduling, process ownership or business-report state is changed.

Native takeover ownership and return controls share the contract in [native session browser](design-native-session-browser.md). Exact device/runtime/native identity, including historical Runs, takes precedence over folder inference; conflicting or unknown ownership is rejected. The shared project lock also protects history clearing/reset, CLI switching, deletion and managed reads, including legacy terminal-only leases. Session-page controls consume existing state updates and the existing scoped return/stop APIs; `nativeTakeover:1` gates preparation on upgraded Workers.

Native Claude inputs carry a fresh UUID; only a matching top-level replay in the resumed session opens that input's output boundary. Group-chat roles' resident Claude (`cli-print-session.mjs`) follows the same rule: it runs with `--replay-user-messages`, each turn's input carries a fresh UUID, delivery is confirmed by that replay, and until it arrives every non-system message (including the result of a notice Claude queued first, such as a background command left by a stopped process) is ignored, so such a reply can no longer end the turn as "no text" and lose the real answer that follows. For ordinary resident inputs that replay also confirms delivery, not the stdin write callback. Before replay, only a top-level `command_lifecycle` with the current `command_uuid` and the session ID captured at send may end the input on `refused`/`discarded`; stopped or finished turns ignore these negative receipts. Home keeps accepted delivery monotonic. Explicit undelivered rejections are excluded from the two-silent-startup-failures queue guard, while genuine startup failures remain protected. Refused inputs may leave a usable resident; discarded inputs close the process and wait for the existing lease exit proof before queue dispatch. No retry or polling is added; missing lifecycle events remain a protocol limitation. Process-wide background-task liveness survives reuse, while visible task tracking resets per input and ignores events before its replay. Home creates task rows only from starts, caps the list at 20, and does not infer child completion or termination from the parent's end. Installed/supported runtimes may read history or prepare an iTerm launch while signed out; operations that send model input still require an available runtime.

The separate native Sessions view (`public/native-sessions.js`) is a human-only browser entry, not an Agent tool or collaboration session. Its filters default to Created sessions and All Agents, querying only dialog-created entries. Manual All sessions selection remains available and survives normal refreshes and tab switches; a fresh page returns to Created sessions. The All sessions view combines the existing independent-history and managed-group scopes with at most two concurrent reads, including titled `nativeCatalogEntries` created by the shared dialog. Home and Worker retain the entry identity separately from the exact vendor session ID; Home can return cached entries while a device is offline. Explicit group filtering uses managed session IDs, while device filtering separates independent histories from those group sessions. Native-session capability 2 prevents older Workers from ignoring these scopes. Operations/focus and a visible-page-only timer refresh the catalogue, with coalesced refreshes and preserved selection/scroll position. Terminal launch still uses the existing private Worker environment, claim identity and iTerm/SSH command builder. Bound project folders retain the project reservation; standalone folders use a terminal-only scope reconciled by the same background return mechanism. No model or managed Run is created for preview, and native terminals receive no platform/role instructions. An explicit page takeover sends user turns through `src/native-turns.mjs` (`nativeTurns:3`): Home records each turn and the Worker resumes the exact native ID in its original folder without a Task/Run or platform/role instructions. Takeover code is isolated in its own modules (`native-turns-home.mjs`, `native-turns-worker.mjs`, `native-turn-sessions.mjs`, `public/locales/native-takeover-zh.js`); Home and Worker forward page operations and share durable terminal leases, capacity and exit verification with the existing execution paths. The shared Codex/print adapters, attachments and global locale remain unchanged. See [native browser contract and acceptance](design-native-session-browser.md).

Page takeovers negotiate `nativePageInstructions:1`. Home attaches the hash-versioned `PAGE_INSTRUCTIONS` only to a Claude/Codex session's first ordinary turn for that version. Worker prepends a hidden system-reminder block; the original stored user prompt is unchanged. Adapter `inputDeliveryState:accepted` receipts travel through NativeTurnRunner independently of terminal status and persist the version in Home's `nativePageInstructions` record. A pre-input stop or rejection leaves it pending; failure after acceptance does not resend it. Compaction/model/effort controls and old Workers are excluded. Side questions still disable the question tool, though their inherited conversation may contain earlier page instructions. No duplicate launch-level hint remains.

Worker-side native history discovery shares an in-flight scan and up to 32 root/runtime cache entries for 20 seconds. Warm reads check the known directories' identities and modification metadata; creation, movement and deletion trigger rediscovery, and an exact-ID miss forces one fresh scan. Header summaries have a separate 500-entry, 20-second LRU keyed by runtime, root and file path, invalidated by file identity, size, modification/change time and Grok sidecar metadata. Detail reads resolve duplicate exact IDs by current file modification times. No message pages are cached: bounded reads, canonical-path and no-follow checks, snapshot identities and cursor validation still run against the original file. These caches add no polling or history writes.

Side questions (`src/native-side-ask.mjs`, `src/native-side-ask-home.mjs`; Sessions page tab "侧问") are a read-only chat beside a Claude or Codex session that never reaches it. The Worker makes one temporary copy per side question: for Claude a session file next to the parent holding its last 10 complete turns (conversation rows only, pictures replaced by a note, a still-running last turn left out), resumed one print turn per question in plan mode; for Codex a `thread/fork` with a read-only sandbox, resumed per question. Home holds side questions in memory only, one at a time; clearing, an hour without use, two hours of age, a Worker restart and a device disconnect all close it, and closing removes the copy (`thread/delete` for Codex). Once created, the side branch retains its own context and replies: accepting a main-session message never closes it, and follow-ups do not re-read the parent prompt or recreate the branch. Files for a side question come from the device's takeover attachment store through `/api/agent/side-asks/:side/:file` while the question is open.

Data retention (`src/data-retention.mjs`) runs on Home and on each Worker a minute after start and daily, under one policy Home sets (Settings → Data; sent with `registered`/`settings`). It reclaims finished sync bookkeeping with terminal results and their transport, journal and cancellation records. Home retains compact owner-and-result-hash receipt proofs so a disconnected Worker can replay a lost acknowledgement after the bulky command is removed. Worker content blobs stay while referenced or while capture/download work is unfinished. A changed plan dependency defers the remaining cleanup after an asynchronous scan or yield; individual blob unlinks occur without a JavaScript interleaving between validation and deletion. Home manifest versions retain the newest N per repository and versions named by bindings, open conflicts or unfinished runs. Chat history, session turns, attachments and run logs are never part of cleanup. Deletion goes in batches of 200 with a yield between; VACUUM runs only while nothing is running (no run, turn, pending sync or query) and only when at least 64 MiB and a quarter of the file is free. `GET /api/data/stats` aggregates Home and online Workers (`data_stats` query); `POST /api/data/cleanup` runs the pass on demand (`data_cleanup`).

Native folder branching reserves its destination with an exclusive directory creation. A failed copy only removes that reservation while its filesystem identity still matches. Linked Git worktrees and submodule pointers are refused before copying; use an independent checkout for folder branching. Regular repositories and non-Git folders retain the existing copy flow. Side-question preparation is owned before asynchronous work starts, so close cancels preparation as well as running input. Failed temporary-history cleanup retains retry evidence. Browser side-question replies and uploads stay bound to the originating session generation and cannot replace a new session's draft.

Native history pagination reads 6 MiB windows and advances to the next window only while no displayable rows have been collected, with a 12 MiB per-request scan ceiling that includes overlapping reads. A page that starts inside a turn carries `turnStartedAt`, the time of that turn's prompt found by a bounded look-back (32 MiB) whose latest answer is cached per history file, so refreshes read only appended bytes. It keeps the existing per-record, prompt-count, response-size and snapshot/cursor checks. A budget-limited empty page carries a notice and an advanced cursor. The timeline places this notice beside the load button, retains it across latest-page refreshes, and advances empty older pages without replacing their existing message nodes. No background scan or automatic follow-up request is added.

The role terminal entry displays `latestTerminalRun` as a summary rather than a history selector. Its new-session action calls the same native form with only device/runtime defaults, leaving the folder and native permissions to the user. Historical resume still uses the Run terminal endpoint; an existing claim retains its actual Run binding and release/stop controls. No history is deleted and the standalone action does not use the group-bound fresh-role terminal endpoint.

`renderMessageMarkdown` recognizes only the complete trailing `wb call --file` document envelope outside code fences. It decodes its text once and reuses the safe Markdown renderer for both group cards and full-screen replies. The reference notice and metadata remain visible; ordinary Markdown, incomplete envelopes, stored text and copy actions remain unchanged. No backend parsing or history rewrite occurs.

Copy controls share the frontend feedback helpers in `role-icons.js`: a successful clipboard write shows a check for three seconds, and stable message/session action keys preserve that deadline across live redraws. Pending group-stop requests show a fixed-size spinner and retain the existing command IDs and error handling. Group-card footers use a compact 36px single-row layout and display execution status plus elapsed time; detailed tools remain in the run log.

Reply streams and complete message snapshots have distinct roles. The Claude print adapter tags stream events with their assistant message identity and emits complete snapshots as message events instead of appending them as text deltas. Native event compaction preserves those identities, and updates the matching saved reply part. The shared read-only reply projection replaces only the corresponding provisional stream; earlier replies, tools and incomplete streams remain. Old events without identities use their existing message/tool boundaries, without rewriting stored history. Native and side-question views supply bounded offsets into their existing text field so a capped event preview cannot truncate a complete retained reply. Synthesized whole-turn aggregate results remain available to backend consumers but are not rendered again beside their source prose.

Run-detail `runTimeline` groups CLI notes with adjacent tools and passes both to the existing Sessions `activityBlock`; its note deduplication, icons and expanders are reused without changing the Sessions module. Empty final-answer payloads do not render protocol JSON. Explicit errors use the existing transcript error style, and stored events remain unchanged.

Native catalogue loading negotiates `nativeCatalogCache:1` with Home. A `cached=1` list query returns only saved Workbench-owned entries without contacting the Worker; normal queries retain ownership checks, pagination and current device verification. Known rows remain during refresh and failed device reads. Worker summaries use a bounded 500-entry identity/metadata cache with no time-only expiration, and publish a metadata-derived `historyRevision`; the frontend skips unchanged selected-history reads while preserving retries after failure and explicit view re-entry. Catalogue previews do not authorize file reads or imply fresh device verification.

The separate browser module `public/output-language.js` converts prose display copies from Traditional to Simplified Chinese without translating English. `room.js` applies it to chat, quotations and attachment Markdown; `document.js` applies it to document Markdown; `app.js` applies it to execution text/results. The UI translation walker also normalizes Chinese prose, excluding raw, code and editable containers. Quotations and mixed Latin/Chinese prose are converted, while code, commands, resource paths and link destinations are protected. Original/history views, copy sources, persisted events and model-facing input are unchanged. The browser uses the pinned `opencc-js` 1.4.2 `t2cn` ESM distribution under `public/vendor/`, registered in Home static assets and the service-worker cache.

`input-language.mjs` separates execution-template language from UI localization. Maintained identity, instruction replacement/revocation and runtime wrapping text uses the English catalog. `executionInstructionComponents` converts only the send copies of custom prose before calculating actual component fingerprints; saved configuration versions remain independently recorded. `createRunInput` converts dynamic task prose once and logs that same copy handed to the adapter. Prepared instruction components and configuration events are not converted again, preserving trusted role names and matching native instruction parameters.

The local `opencc-js` dictionary uses standard Simplified-to-Traditional conversion without a model request or native binary. Code fences, indented code, known command/code lines, executable paths, identifiers and exact quoted strings retain their originals. Ambiguous bare ASCII executables followed by Chinese text also retain the whole line rather than risk renaming an argument; this can preserve mixed prose such as an ASCII product name followed by Chinese. Marking code explicitly gives unambiguous protection. Trusted roster and source-author names are quoted before the send copy is converted. All four managed adapters use this path for initial input, retained-process continuation and exact-session resume. UI language changes alone do not invalidate instruction fingerprints. Existing native history, tool results, attachments and direct manual terminal input are outside this transformation. The background organizer uses English maintained templates but preserves its original structured material and UTF-16 coverage ranges; its source material is not a managed-dialogue send copy. Rolling installation keeps the existing Home/Worker protocol; devices running older Workers retain their old behavior and must be upgraded before this policy is claimed for them. Saved user-authored platform, supervisor and role prompts are not automatically translated to English.

Role history is a tab in the ordinary role editor and the supervisor settings; cards retain only the terminal action. Clearing history archives and marks that role's platform sessions, removes their native-session associations, and hides its previous runs from terminal candidates. The next dispatch creates a new platform/native session. Shared project chat, code files, other roles and audit records remain intact. The authenticated clear endpoint checks the expected current session and rejects unfinished work, CLI switches and terminal takeover, including takeover of historical runs on previous devices. Cleared session IDs cannot be read through session tools or resumed through the terminal endpoint. This is a fresh start, not recovery of missing vendor history.

Role configuration supports persisted, reversible CLI switching on the same device. Codex and Grok perform an original-session handoff, verify a staged successor and commit the binding only after process settlement; cancellation before commit keeps the original binding. Claude and Antigravity switching remains explicitly unavailable until its native maintenance path is verified. See [design-role-cli-switch.md](design-role-cli-switch.md) for the supported scope and acceptance boundary.

Git delivery help is local and never submits a request. Delivery arguments are validated before contacting Home. For project-scoped Runs without a legacy role repository URL, an explicit SHA may use the sole repository captured on that Run; multiple repositories require the existing `auto`/items form. Approval and fixed-commit publication remain separate from updating a target checkout, and uncommitted files are not included. Supervisor guidance distinguishes a Git-hosting ref from the actual version in a device's bound directory.

### Shared role instructions

`sourceInputBatch` validates code-input batch ownership, purpose and terminal availability both before call/schedule admission and when legacy queued work is reconciled. Directory receipts are never accepted as `sourceSyncBatchId`; document readiness is checked separately with sync status and target hashes. A failed admission rolls back partial Task creation, records `admissionError` and `notExecutedReason` on the original unstarted request, and uses the ordinary queue/continuation settlement path without creating a Run or changing reports. These requests leave the scheduler until explicitly corrected through a new valid request; same-ID replay does not restart them. Materialized tasks and active/unknown Runs are not terminalized by this path. Home isolates individual request failures and guards every synchronous chat-scheduling entry point, with bounded diagnostic text and repeated-error logging. Database/storage failures remain operational errors, not successful admissions.

`agent-calls.mjs` atomically accepts one or more role targets through the existing calls endpoint. The CLI repeats `--role`; the endpoint accepts a `roles` array or the legacy `role` string. One room message owns the common text and recipient snapshots, while `coordinationRequests` retain separate stable IDs, provenance, limits and execution state. All recipients validate in one transaction; same-ID replay checks the target set and content. Single-role IDs and the compatibility `ask` identity remain unchanged. `callMessageId` keeps direct results, notes and continuations linked to the shared instruction. Session receipts bind every addressed request, including several requests routed to one supervisor, and cannot create a second broadcast driver. Explicit execution order still belongs to the schedule API.

Sent cards represent message acceptance, not receiver completion: the sender's card is completed once registered, without recipient counts. Each receiver has an independent live reply/progress view. `Rooms.replySourceFor` resolves the immediate public call (including shared-call and continuation identities), with project/conversation and visibility checks. The recent messages response includes bounded `liveReplySources` excerpts so pagination does not replace a role's instruction with ancestral user input. Legacy ancestral result/note quotes are corrected only in the read projection; explicit replies and stored history remain unchanged. Quoted previews open the original viewer. Card footer actions remain local to the card.

Message bodies retain the existing `16em` maximum height with internal scrolling instead of line clamping. Before rebuilding the feed, the browser snapshots per-preview scroll offsets keyed by project and message/Run identity and restores matching entries afterward; switching projects does not transfer offsets between messages. The full-screen reader and stored content are unchanged.

### Human queue steering

For peer preservation, an already-dispatched nonterminal Run includes a queued or unconfirmed launch: Home cannot infer that the Worker has not started it. `POST /api/projects/:projectId/tasks/:taskId/steer` only promotes a human group-chat Task that has not started. Ordinary sends never request interruption. An open wait is never cancelled by a steer; a steered message for a waiting role simply runs first and the wait keeps its queue slot. The direction-change notice is sent only when a running turn was actually stopped. This cancellation preserves already-running peer requests with their continuation ancestry and descendants, so their results remain attributable without restarting the cancelled owner. Generic cancellation still cancels the whole call tree. The original role session lock is released by the Worker's terminal event after process exit, and the new Run reuses the exact native ID. `steeringWaitReason` blocks early dispatch in both Rooms and Store, and a queued steering message goes ahead of other queued items. ### Cross-device attachment transfer

- `Attachments` is still the only source of project attachments. `AttachmentTransfers` uses the existing Worker query to determine the target directory from the project binding and creates no Task or Run. `POST /api/projects/:id/attachment-transfers` takes a client idempotency ID, a node and an attachment ID. Duplicate in-flight requests are merged, a failure can be retried explicitly with the same ID, and a success returns the original receipt. An offline device is not silently replaced by another.
- Media streaming (`src/media-streams.mjs` on Home, `src/media-files.mjs` on Workers with capability `mediaStream: 1`): `GET /api/runs/:id/media?path=` and `GET /api/native-sessions/:node/media?runtime=&sessionId=&path=` resolve a path only inside the run's workspace/bound roots or the registered native session's working directory, ask the source Worker for `media_stat` (realpath inside the root, hidden and credential-like components refused, type from header bytes) and return metadata plus a ticket. The ticket is an HMAC over node, root, path, size, mtime, inode/device, type and an expiry at the end of the following UTC day, signed with a per-process secret; it is the only credential of `GET /media/<ticket>`, which is served before the API-token gate, rejects cross-site fetches, supports single Range requests (open-ended preview ranges capped at 8 MB), and serves non-media types and `?download=1` as attachments with `nosniff`. Each range is one relay: Home sends `media_stream` with a per-relay secret over the WebSocket, the Worker re-checks the version and POSTs the bytes to `/api/worker/media-streams/:id`, and Home pipes them to the browser with backpressure; at most four relays per device run at once, others wait up to 20 seconds. A changed file answers 409 `file_changed`, an offline source 503, an old Worker 501. `POST /api/projects/:id/media-transfers` hashes the source (`media_hash`), has the target pull the file through the same relay into `.workbench/tmp/media/<transfer>/` (`media_receive`, written as it arrives, size and SHA-256 verified before rename) and records progress from relayed bytes in `mediaTransfers`; a completed copy on an online device is used by `describe` while the source is offline. Directory and working-tree sync captures record a file over the per-file limit that is not in the device's baseline as an `oversize` exclusion instead of failing the batch; Home still fences previously synchronized paths.

Home caches complete, version-verified media files on disk, up to 256 MiB per file and 2 GiB total, with ten-day idle eviction. A compact descriptor is persisted only with a complete version, enabling a fresh offline description after Home restarts. Cached reads still require the currently registered device and directory authorization; an old signed ticket is not a directory grant. Missing or corrupt descriptors cannot broaden access, and eviction removes orphan descriptors. Browser image navigation keeps focus inside the viewer when switching pictures.

Native history refreshes can request bounded appended-row deltas from an exact file snapshot. The browser saves bounded latest-page copies for up to thirty sessions in IndexedDB, keyed by device/runtime/catalog entry and checked against the native session ID. Unchanged turns reuse their DOM, but cache keys include the actual prompt, text and tool content so same-length replacements render correctly. A background delta overflow preserves loaded pages, cursor, snapshot and scroll position and exposes the explicit latest-history refresh; only that user action replaces the loaded view. New Workers advertise `nativeToolDetails: 1`: opted-in native history pages carry at most 15 visible prompts plus lightweight tool summaries. Exact tool input/output is read only after expansion of the selected step, in 16,384-character chunks bound to the registered file and record bytes. Recent browser copies are trimmed with a valid older cursor; revalidation retains the current same-session preview. See [design-lazy-native-tools](design-lazy-native-tools.md) for protocol and compatibility boundaries.

- The Worker declares `attachmentTransfer=1`. `attachments_receive` and the automatic download of a Run share `receiveAttachments`, and files land in `.workbench/tmp/attachments/<transferId or runId>/`. Each directory level is checked against escaping the workspace, the size and SHA-256 are verified, and a temporary file is renamed atomically. The extension is kept and the display name is separate from the on-disk name. A standalone download is allowed only for the Worker credential and the attachment set currently being transferred.
- The Home stores `attachmentTransfers` receipts so the UI can show the path. A Run reports the actual paths through the `attachmentFiles` state, and role prompts inject those paths. Temporary files are not cleaned automatically, are not mixed into Git delivery, and no additional file sync service is introduced.

### Supervisor stall reminders

`proactive-followup.mjs` is called by the existing Home scheduling tick, not an independent scheduler or classifier. Project settings persist `proactiveFollowups` with a default-on switch (explicit off is preserved), integer silence duration (1–10080 minutes, default 10), revision and message cursor. `room_message_receipts` supplies immutable first-write Home timestamps and monotonic SQLite receipt sequence numbers; first observation or explicit enabling snapshots the current tail, so old chats are not replayed. Discovery and processing use `(kind,id)` keyset pages of 100 per kind, at most once per 15 seconds inside the existing tick; large installations cycle over pages rather than scanning all groups every second. Message observation reads only arrivals after each cursor. This bounds groups per tick; processing a large backlog may take multiple cycles. Explicit follow-up provenance is resolved through stored Task/Run/request/discussion links. Monitor tasks expose their exact message references for deduplication, without changing their schedules or anomaly policy.

Chats with `conversationTasks` use task state as authority. `ConversationTasks` updates a Home-only `conversationTaskActivity` aggregate (total/open counts and a monotonic version) in the same SQLite transaction as create/update/transfer; idempotent create does not advance it. An existing chat initializes counts once through the scoped task index; steady ticks read one small record, never full task descriptions/history. Explicit off still wins. All tasks done/cancelled clears the anchor and withdraws only unstarted reminders; no message arrivals or final-result traversal are read for that chat. Creating, changing or reopening tasks starts a fresh silence window at the current message tail. Subsequent eligible messages reset the window; an unchanged task/message anchor is notified only once across restarts. Running or queued work postpones the window. Admission rechecks task state so closing tasks cannot launch a stale queued reminder. The reminder includes open/total task counts; details are available with `wb task list/show`.

Only chats with no task records use the message fallback below. A successful role reply cannot close an unfinished conversation task.

A final `result-<runId>` anchor is settled without a reminder only when its same-chat Run succeeded, has no handoff wait and its request/continuation lineage has no unfinished descendant calls or transfers. Notes and reply text do not prove completion. Running/queued work postpones the window; a dormant discussion wait alone does not. Due reminders include bounded request/transfer facts and the latest failed/interrupted Run in the same chat, refreshed at actual admission. Due events atomically create one internal platform message plus an ordinary Task and coordination Request. Before `Store.startTask` claims a Run, the event's message anchor, switch and duration are checked again. New normal messages and disabling withdraw unstarted initial turns only; active turns and dependency continuations keep their original relationship. The supervisor uses its current saved configuration and normal role-session/capacity/workspace locks. Errors and waiting reasons remain attached to the real Task/Request/Run.

Background supervisor Runs retain their input and output for details and the read-only live scene, but do not create a normal streaming chat bubble or an automatic completion message. Explicit `wb note` remains public; `needs_input` reports and native approvals retain their user-facing entry points. A platform event and bounded recent excerpts supply context without expanding shared prompts; full history remains on demand. No IM integration is added. See `design-supervisor-proactive-followup.md` for the feature contract.

### Native terminal lifecycle

The session-page queue retains ordinary sends as `waiting`; only explicit Steer reorders and requests interruption. A nonresident process ending normally must have its matching lease closure confirmed before the next turn starts. Stale closure receipts cannot cancel another lease's queue. Unexpected process closure, explicit release and Home recovery retain cancelled messages and reasons rather than silently resuming them. A lost Worker connection is first a grace period, not an ending: the Worker keeps its turns running for 3 minutes and buffers their reports (`NativeTurnRunner.suspend/resume`), Home marks the turns `disconnectedAt` for the page and waits 4 minutes; the Worker's next registration names the turns it still runs, the others end as lost, and only an expired grace ends them all as a disconnect used to. Home's heartbeat ends a Worker connection after three silent 15-second intervals, and any received frame counts as life. Queue admission and credential failures are recorded per message and do not leave later messages stranded behind an inactive head; credentials are resolved at dispatch and never persisted in queued turns. The composer is mounted once so quiet refresh preserves focus and text. Native history text/tool fragments have stable distinct IDs even when they share a JSONL offset.

Native catalogues are Workbench-owned only. Home derives ownership from created catalog entries, uncleared managed role-session bindings and recorded native terminal/page takeovers; browser-provided titles, project-folder matches and arbitrary native IDs cannot grant read access. Workers advertise `nativeSessionOwnership:1`; Home refuses old Workers before catalogue/history reads instead of falling back to vendor scans. The All view combines registered independent/takeover entries with managed groups, including under device filters. A browser refresh discards legacy vendor entries rather than retaining them as a failed-device fallback.

History lookup never traverses vendor transcript directories. Codex uses a read-only exact-ID query of its existing `state_*.sqlite` thread index; Claude resolves the registered workspace's encoded project path and exact session filename; Grok and Agy use exact ID paths. Index discovery may list only the Codex configuration root's database filenames, never session directories or other transcript rows. Missing indexes/workspaces/files remain explicitly unavailable, with no broad-search fallback. All reads retain native-root, symlink and pagination checks. Registered takeovers remain visible after release; stop/release controls retain their original leases. This change performs no vendor-file deletion or production history migration.

The Sessions sidebar uses `public/native-session-groups.js` with authoritative cross-project `roleBinding` metadata from the native catalogue API, not the current project's workspace snapshot. Home pages managed bindings in batches of 50 before querying the Worker, and the browser follows group-page cursors within the existing two-job concurrency limit. Unambiguous project/group/role IDs define presentation groups, independent of labels, CLI and device changes. Creation time selects the latest entry, with generation breaking ties; transcript modification time cannot promote an older session. The sidebar displays only that latest entry. `public/native-history-timeline.js` loads older messages and then prior sessions inside the chat scroll pane, preserving the reading position and section identities. Its generation invalidates late responses after selection changes. A current successful latest-page read clears only that read's transient error before the unchanged-content shortcut; older-page failures and unread-gap notices remain separate. Recovery without content changes leaves the history DOM and reading position intact. Only the selected session's history element is supplied to page takeover, so displaying old messages cannot redirect send/release actions or duplicate live-turn decorations into historical sections. Missing, cleared or ambiguous bindings stay separate. No records are deleted or archived and no new polling is introduced. Independent-session catalogue limits remain explicit; missing readable transcripts do not remove their managed history entries.

Native history GETs opt into `historyPage=1` and require Worker capability `nativeHistoryPages:1`; older Workers are rejected before an unbounded legacy preview can be mistaken for a page. All `readNativeSession` callers supply a saved Workbench identity; the page path reads backward at JSONL line boundaries (a 6 MiB window per scan, 45 user prompts with their reply/tool fragments and 768 KiB encoded message data per reply). Cursors bind runtime/session/file identity and pin a tail boundary so normal append does not shift older pages. Replacement, truncation or a changed pinned tail fails visibly. A single record longer than the window (a tool result carrying a screenshot is one JSONL line of 1 MiB or more) widens that read until the record is whole, up to 32 MiB; only a record past that cap is reported as too large, never silently skipped. Original native files remain authoritative and read-only. Quiet refresh supplies the previous `historySnapshot`, including for exhausted short files, and validates it before merging a new tail. An unobserved large burst offers an explicit latest-view refresh rather than silently bridging a gap. The initial page must finish before upward paging is enabled. An unreadable session or remainder keeps its identity/error visible and offers an explicit continue-to-earlier action; it never deletes the failed source or silently treats it as complete. Scrolling triggers one in-flight read, not a new background poll or a full transcript load.

Role cards expose one live-scene entry, without a separate terminal button. The scene header offers New session and Resume session, including when the role has no recorded Runs. New session opens the existing independent native-session form with device and CLI defaults only, without group history or a preselected workspace. Resume session opens the confirmation dialog for the latest resumable Run; opening either form does not start a CLI or acquire a terminal. Runs without valid native IDs and cleared histories are omitted from recovery; an existing takeover keeps its original binding and return controls. Stored executions, input/output events and native transcripts are not deleted, and the role-history tab retains its existing records.

`public/live-scene.js` provides an independent read-only dialog from role cards only. It reads authenticated Run detail and pages the existing events endpoint with `after` and optional `limit` (1–1000); paged responses include `hasMore` and a small `runState` snapshot. Legacy requests retain their original response shape. Viewing never sends terminal preparation, resume, stop or dispatch operations. Initial reads and incremental polling reconnect; closing cancels browser reads only. Generation checks isolate project/Run switches. Unchanged DOM is preserved while output arrives and manual scrolling pauses following. The scene uses white surfaces with dark text; the header's jump-to-bottom icon scrolls to the latest event and resumes following.

The scene presents the actual saved input snapshot, output and tool lifecycle records, not hidden native instructions or reasoning. Stable tool IDs merge streamed deltas and final snapshots. Codex command deltas and completed tool results, Claude/Grok tool results, and Agy step updates retain bounded output with explicit truncation flags. A native summary remains a summary: Agy `view_file` can expose only line/byte counts, and the viewer does not reread a file to manufacture the missing result. Historical unrecorded input/results cannot be recovered by opening the viewer.

The role-card terminal entry defaults to **New session**, including after history was cleared or before any Run exists. Authenticated `POST /api/projects/:projectId/roles/:roleId/terminal` prepares/releases a manual native terminal with a stable operation ID. It resolves the current role device, model and bound project directory; no historical Run or native ID is fabricated. Shared and role execution prompts are supplied, but the owner's responsibility is not injected. The native user/environment remains private on Worker. This terminal does not replace the role's managed session mapping or send its conversation back to the project chat; managed `wb` tools remain unavailable.

Cloud terminal dialogs show the registered SSH destination and explicitly offer **Open new session via SSH**, **Resume via SSH**, and **Copy SSH command**. New sessions and historical resumes both use the existing `ssh -t` launcher with that device's host/port/user, switching to the Worker user when different. The browser-side terminal must be able to reach and authenticate to the server; a stored Home password is never embedded in a command or URL. Missing server registrations do not fall back to running locally.

`terminalLaunchView` percent-encodes the command for the iTerm URL rather than using form-encoded `+` spaces. New preparations, repeated prepare responses and state snapshots all use this view, so previously saved incorrect links are corrected on read without changing command text, lease IDs, native history or takeover locks.

Worker capability `terminalFresh:1` gates new-session preparation. Role/CLI switching, active or unreconciled processes, node capacity and project takeover locks are checked again after asynchronous directory validation. Released requests are tombstoned; late prepare replies cannot recreate their locks, and a successful return rotates the dialog operation ID for the next fresh session. New wrapper launches recheck the canonical directory. Existing past Runs remain selectable and continue through the exact-native-ID resume endpoint unchanged. Closing the dialog alone does not release an already prepared terminal: use **Return to platform** after its CLI exits.

- Run events support incremental reads with `after` sequence numbers. `public/room.js` de-duplicates streaming increments and completion snapshots, a fullscreen view is bound to project/task/run and keeps the body after completion, and scrolling up manually pauses following. The full text is kept.
- The adapter stores `nativeSessionId`, and the Worker adds the original user, CLI path and session storage environment. The original CLI environment, including authentication and proxy settings, is stored only in the Worker's `runtimeEnvironments`, never sent back in status events, and excludes WB and platform credentials.
- `src/terminal-resume.mjs` defines four resume commands, history verification, the project-node takeover lock and the interactive wrapper. `prepare` of `POST /api/runs/:id/terminal` reserves the lock on the Home, and the Worker then verifies that the original process has exited, the original directory and the vendor history. An iTerm command URL starts the wrapper; SSH uses the registered host and switches to the original Worker user if necessary. Old executions without an environment record are refused.
- The wrapper and the release use Worker SQLite write transactions to coordinate. A prepared ID can be claimed only once, and on release it is atomically checked that the wrapper and child process have exited. Project deletion, queue dispatch, Worker start and managed Git publication are all protected by the takeover lock. The lock survives Home and Worker restarts and is not released automatically when the device is offline or the state is uncertain. New conversation in the terminal does not flow back to the group chat, the `wb` bridge is not restored automatically, and processes started manually by others are not covered by this lock.

### Per-device CLI capacity

Each device card shows and edits a shared CLI limit (integer 1–64) through authenticated `POST /api/workers/:nodeId/capacity`. Home persists it in `workerConfigs`; the Worker persists its applied value separately and advertises `cliCapacity:1`. Active/preparing role runs, retained idle processes, background organizers and prepared/active terminal takeovers share the device limit. Short-lived, no-inference runtime discovery probes and manually started external CLIs are not managed execution slots.

Home queues tasks by device capacity. Worker independently reserves slots before asynchronous launch preparation and defers a full-device launch without acknowledging or failing it; retransmission keeps the same command, immutable input and role/native-session IDs. Cancelling a deferred launch records a settled interruption, so a late delivery cannot revive it. `capacity_state` wakes pending work without triggering another quota probe. Lowering the limit never interrupts admitted runs; they drain first. Idle processes are reclaimed oldest first, and their actual exit is awaited before replacement. With spare capacity an eligible role reuses its live process; after retirement it resumes the exact persisted native session, and unsupported keep-alive adapters continue through their existing native resume path.

Saved offline limits remain pending and are applied on reconnect before `ready`. Older Workers cannot apply this protocol and must be upgraded before an online edit; Home never allocates them above their reported concurrency. Folder/name edits preserve the saved limit. Manual terminal preparation reserves capacity on Home before Worker verification, but a full device returns a clear wait error instead of opening another CLI.

### Collaboration efficiency increments

`public/execution-progress.js` is the shared read-only execution-progress projection used by Home message progress and browser chat, role, plan-member and task-detail displays. It maps existing records into six display states (`queued/running/waiting/completed/stopped/error`), with transport phases, waiting reasons and timestamps retained as details. No parallel persistent state machine is introduced. Unknown processes remain waiting for reconciliation; cancellation does not imply process exit. Compact workspace snapshots omit reply bodies and cannot by themselves establish an empty response. Historical Runs and peer-discussion turns do not inherit the current task's waits or acceptance.

The plan dock specializes labels without changing persisted states: a failed request with `notExecutedReason` and no Run identity is **Not executed**, while stopped execution is **Aborted** and actual failures remain **Execution error**. Blocked/failed plan headers show **Plan error** instead of an ordinary wait. Missing Run details alone are not proof of non-execution. Stop-confirmation and instruction-completion displays remain unchanged.

`RoleCalls.finish` records a normally completed delivery as `succeeded`, independently of the report verdict; an empty consultation without a substantive final answer or report is an `incomplete_output` delivery failure. `outcomeFor` reads only the saved report, otherwise `unverified`, rather than manufacturing a negative verdict from a process error. Dependency waits, continuation identity and cancellation fences are unchanged. Existing execution-plan stop/report policies retain their previous admission conditions explicitly after this separation; the change adds no review order, automatic rework or approval policy. Old terminal records are not migrated or retried, and the UI uses available execution evidence without rewriting those records. Verdicts are displayed in the delivery report, not in execution-progress badges.

`consultRound` remains historical continuation metadata, not an admission quota: schedule completion and replies from different reviewers must not consume a shared three-round allowance. RoleCalls retains its root limit of twenty non-continuation requests, depth/cycle checks, idempotency and cancelled-parent validation. No old requests or reports are rewritten when this check changes.

There is no platform-wide pause of remote execution: the former `settings.main.paused` switch was removed and Home deletes a stored flag at startup. Stopping, reconciling, disconnected and ended runs cannot send agent operations. A Worker refuses commands, queries, native turns and side questions until Home has accepted its registration and again once the connection drops (`homeDisconnected` in `src/worker.mjs`); this connection guard is not user-controlled. Reports reject exact probe placeholders without claiming to semantically validate evidence. Print tool results retain up to 12,000 characters of output independently of assistant text; process success still does not prove a business verdict was accepted.

Bridge responses are fully written to a private temporary file before same-directory hard-link publication. A reader sees either no response or a complete response; an existing final response is never overwritten. This changes neither the operation identity nor retry policy. Cleanup waits for in-flight handlers and removes only this turn's bridge artifacts.

Managed recovery checks run after normal dispatch gates, once per native target in a scheduling pass, while accepted recovery-wait launches keep their original retry path. Each check obtains one fresh asynchronous process snapshot instead of running synchronous process queries for every historical turn. Missing/partial evidence remains unknown; reclaim and stop still revalidate startup identities before signals. A recovered launch emits an ordered starting transition before acknowledgment. Codex metadata probes remember transport closure across optional quota errors rather than issuing another RPC to a dead process.

- `src/result-receipts.mjs` keeps `resultReceipts` records owned by the calling role, one per call, Run and report revision. `saveRunReport` and `RoleCalls.finish` register them idempotently (replays and Home restarts refresh status facts only; an older revision is marked superseded, never overwritten). Store launch claims the owner's undelivered, review-visible receipts into that Run's `contextPacket.receipts` at the safe launch point; they become delivered only when the CLI accepts the input (or the turn succeeds), and an ended Run that never accepted input releases its claim. `wb progress verify` records the owner's accepted/rejected decision with history; `wb progress` derives per-item stages from receipts and decisions, treating a pass for a different SHA as stale. Only a call settling now creates a receipt: replaying calls that had already settled (restart, upgrade) refreshes existing receipts and never backfills history, and receipts an earlier replay created for long-settled calls are archived at Home start (kept, counted by `wb progress`, never delivered). `timer-monitor` adds a receipt finding only while the owner is idle in that chat, keyed by the newest receipt, so unchanged state wakes nobody. Reports may add a full 40-hex `version`, a `stage` and an `item`; merged/deployed require `version`, and the fingerprint includes these fields only when present.
- Run-less outcome receipts (`registerCallOutcome`) record a call that produced no Run result, keyed by request, outcome and episode so each transition is told once and replays add nothing: `RoleCalls.failAdmission` (`not_executed`), `RoleCalls.cancel` for a child whose caller is neither cancelled in the same operation nor settled (`cancelled`), and the Rooms scheduler for a blocked target (`blocked`, episode `kind:blockedSince`; immediately for `role_disabled`, after `BLOCKED_NOTICE_MS` for `device_offline`/`cli_unavailable`). Busy roles, capacity, workspace exclusivity and Worker upgrades remain plain queueing. Outcome receipts are never archived as replay history. Verification accepts `receiptIds` (at most 50, each settled in its own transaction and reported separately) and the `acknowledged` decision, which keeps the item's verdict and blocker and never yields `verified_passed`.
- Resume continuity: `RoleCalls.create` lets a continuation through when its source call merely settled (succeeded or failed) and refuses it only for a cancelled or redirected source; new calls still need a live source. `resume` closes a wait whose source was cancelled or redirected as `cancelled`/`source_cancelled` (replies kept, no continuation, no receipt). A failed continuation creation goes to `resumeFailed`: storage errors keep the wait with `resumeError.kind=transient` (page stage `resume_retrying`) and retry on the next scheduling pass with the same deterministic continuation ID, up to three attempts; any other error ends the request as `failed`/`resume_failed`, settles its chain and session queue, and registers one `resume_failed` outcome receipt for the delegating role. `reconcileStuckWaits` runs once at Home start before result replay: a `waiting_call` with a recorded `waitingReason`, no continuation and all dependencies settled more than `STALE_WAIT_MS` ago is ended as `resume_failed` (`resumeError.kind=stale`) without receipts or parent resumes; recent ones and waits held without a recorded failure (paused Home, running plan, discussion) are left alone.
- Agent refusals are coded end to end. Home's agent guard returns `run_reconciling`, `run_stopping` or `run_ended`; the Worker bridge derives the same codes from its local state (`agentOperationBlock`, plus `home_disconnected` while it is not registered with Home) before forwarding. `agentRequest` retries only `run_reconciling` and `home_disconnected`, which were refused before any work, reusing the identical payload and request ID; other errors, including outcome-unknown transport failures, are returned once with a `[code]` prefix.

Project deletion removes `runReportFiles` and `resultReceipts`.
- `SourceSyncAgent.fileStatus` answers `wb sync status {"path"}` from canonical manifests, per-device acknowledged entries (`updatedAt` as observation time), open conflicts and queued/capturing/applying batches; it never infers arrival from project-level status, treats offline or unacknowledged devices as `unknown`, and hides hashes of unreleased review documents under `.workbench/`.
- `src/run-reports.mjs` receives the structured verdicts `passed/failed/blocked/needs_input` of an active Run. Exit status and business verdict are stored separately. By default, stages of `executionPlans.requiresReports` advance only with a passing verdict and a complete version; old history is not forcibly migrated to "passed". - `src/history.mjs` provides search and paging over messages, Runs and calls of the same project. Tool logs are not mixed into the report.

Home runs one batch at a time, only when conversation organizing is idle and the device has a free slot, through the Worker action `memory_organize` (capability `memoryOrganizer=1`, tool-less `runModelPrompt`, 5-minute limit); a slot lost to business work is retried after a minute without counting as a failure. A batch is up to 60 messages and 60000 bytes of serialized JSON (4000 characters per message) of one chat in receipt order, with each author's CLI and device, the closest existing entries with their source project and the project's `AGENTS.md` read from an online folder (it outranks only that project's own material, never entries learned in other projects); the prompt stays under 120000 bytes because it is one command-line argument, dropping context and then trailing messages if needed. The answer (`add`/`update`/`supersede`) is applied with the watermark move in one transaction; malformed items are dropped, a stale batch or a deleted project is refused, `edited` and superseded entries are never changed. Preferences and rules for one project are not recorded; roles write those into that project's `AGENTS.md`, which every CLI reads. Entries people saved are corrected in place when newer messages change them, never copied. Once a day (and after "Organize now"), when no project is ready to organize, a duplicate check runs: each entry with its closest neighbours (sharing rarer terms and at least 60% of the smaller entry's terms) forms a group of up to 12, so a change only alters the groups it is in; groups are cached until an entry changes. Up to 20 groups per call, within the prompt limit, go to the same organizer model, which merges repeats and, for a conflict (the same property of the same device, service or account), keeps the entry whose fact was said latest (`saidAt`, from its source messages or a person's edit; a person's entry wins a tie). Merged-away entries are deleted. A merge is refused when it chains onto an entry already used in that answer, touches an entry changed since it was sent, exceeds the length limit or drops a key-like string of a secret; organizing answers likewise only change entries as the model saw them, and over-long text is dropped rather than cut. Groups left as they were are not sent again until their content changes; groups failing three times are set aside (signatures of current groups in `memoryProgress` `@consolidate`). The organizer's first setup can start "only from now on", which moves every chat's watermark to its current last message. Its CLI process gets the prompt on stdin (Claude, Codex) or a private file in its temporary folder (Grok, `--prompt-file`); Agy only takes an argument and keeps nothing: Claude runs with `--no-session-persistence` (its empty project folder is removed), Codex is ephemeral, and the Grok session folder and the Agy conversation files of that run are deleted afterwards; the same applies to background conversation organizing. AGENTS.md is read once per request of a project. Nothing on the hot paths reads old history or every entry anew: each project's backlog is counted incrementally from the receipts after the last one seen (through the project/seq index; a fresh Home starts from `caughtUpSeq`, the receipt where the project was last caught up), the per-second check reads only memory-progress records with a request, judged group signatures live in their own `memoryChecks` record, search terms and filter text are cached per entry while it is unchanged, and the settings list only redraws while its tab is shown. Roles see `wb memory search` in the per-turn tool line. Sessions-page CLIs started by the Worker get `wb` first on PATH (the Worker's node folder only last) with `WB_NATIVE=1` and `WB_BRIDGE` set to a per-session folder under the Worker's data (writable for Codex); only folders of sessions driven in the last 12 hours are scanned, and all are cleared when the Worker starts; that `wb` only offers memory search, the Worker relays it to `/api/agent/native-memory/search` with the session's CLI and its device, and the page instructions mention it once per session; these CLIs no longer inherit the Worker token. People page through, filter (words and type, on Home, 50 per page), add, edit and delete entries in Settings → Memory (`/api/memories?query=&type=&offset=&limit=`); deleting a project keeps the entries learned there and removes its watermarks.
- `startTask` reads the actual summary and the full range of messages at that moment in one transaction and freezes them into `contextPacket`. Uncovered body text has a 12000-character budget, favors recent human messages and allows at most 1000 characters per item. The directory lists at most 100 items, the number and range beyond that are saved explicitly, and omission is never treated as having read. Live and final cards share the source-message ordering boundary, including when the source timestamp is slightly later than the Run. A previous Run stays visible if its task starts another Run before history catches up. The prediction is judged afresh on each attempt, kept on the draft across a reload, and ends once Home's tasks are known (matched by `sourceMessageId` while the POST is still in flight); a send that failed stays in the chat with its actions. A message whose tasks were all cancelled before starting (cancelled or taken back from the queue) reached nobody and is not shown in the conversation. On the Sessions page a live turn puts its background-task block before the closing prose, as the history drawing does, so nothing reorders when the turn ends.

## Project directories and repository configuration

New standalone native-session dialogs use `POST /api/native-sessions/:nodeId/default-folder`. Home forwards only the node's project/repository bindings; a Worker advertising `nativeDefaultFolder:1` prepares `native-sessions` below its configured workspace root. Canonical-path checks reject managed-project overlap, symlinks, files and unavailable permissions without modifying existing contents. The UI ignores late results after device changes, manual selection or closing. Existing-session resume and all terminal occupancy guards remain unchanged; old Workers require manual folder selection or an upgrade.

`GET /api/workers/:id/directories` is a human-only query to a Worker declaring `projectBrowser`. Local Workers with `localFolderSelection:1` can list accessible filesystem directories, including hidden directories and mounted volumes; remote and older Workers retain their configured roots. Each query lists one directory level, at most 200 entries per page, without scanning files or creating execution grants. Symbolic-link entries are not listed; direct input is canonicalized. Home does not read the user's machine.

`FolderPreparations` persists creation intentions before contacting Worker. Failed or abandoned preparations are compensated immediately when idle is confirmed, or retried by existing terminal reconciliation after reconnect. Current bindings and successful/active terminal claims are retained. Worker records cancellation even before a delayed preparation arrives, and rechecks the latest receipt after asynchronous directory identity checks so late activation cannot overwrite revocation. Native cleanup uses the existing PID-identity release check without terminating a process. Only a confirmed cleanup adds `folderPreparationReleased` to the error response, allowing the native/project form to renew its operation ID without discarding inputs; unknown outcomes retain the old ID.

Creating a project requires `folderName` and `supervisor={nodeId,runtime,model,effort,permissionScope}`. Home validates online status, authentication, model and capabilities. With no `localRoot`, Worker retains the default child-directory creation flow. An upgraded local Worker can instead prepare an explicitly selected existing directory without bootstrap files or Git changes. Home persists its binding and grant together before issuing scoped authorization. The supervisor permission selector remains explicit and does not silently grant device-wide CLI access. Project queries, execution plans, native turns and synchronization retries carry their actual project/native identity; path matching alone never borrows a grant. Rebinding, deletion, native cancellation and reconnect reconciliation invalidate obsolete receipts without deleting files or history. Active execution and terminal occupancy guards remain in force. This routing boundary does not add an OS sandbox to a native CLI configured for bypass.

A Project may still carry the legacy single `repoUrl` and `repository` (owner/repo/webUrl); the page no longer edits it, and `POST /api/projects/:id` without `repoUrl` keeps the stored value, so older single-repository projects deliver as before. Repositories are managed as project repositories. The former `git-check` route and Worker query are removed.

When no account was picked, a repository URL uses a hosting account matched by `hosting.match(url)`: the only account whose space owns the repository, else the default account (`settings.main.hostingAccountId`) if it is on the same platform, else the platform's only account. Several equally possible accounts are an error for project repositories. Creating a new repository still names the account to create under. Native sessions use a narrower rule, since their token lands in a per-session Git config the CLI can read: an account bound earlier keeps applying while it exists and the folder's remote is unchanged; a session set to the device's own credentials (`hostingAccountId: null`) stays so; otherwise only an HTTPS remote in a space one account owns (`match(url, {ownerOnly:true})`) gets that account's token. SSH remotes keep the device's key, and a repository in nobody's space gets none. Home reads the folder's remote once from the device (`native_workspace_git`, 5 s), remembers it, including that there is none, in `nativeSessionSettings` (`repoUrl`, `remoteChecked`), and the Git card refreshes it; a changed remote drops an account bound for the old one. Queued turns resolve the credential the same way as immediate ones.

## Conversation and roles

### Parallel group chats and team-only copies

`group-conversations.mjs` adds group identity above project-owned configuration. Missing historical `conversationId` resolves to `projectId`; explicit cross-project/unknown IDs are rejected. `RoleSession.groupConversationId` owns the group while its existing `conversationId` may remain a source-isolation native partition. New chats reference the same roles and workspaces but create native sessions lazily, without old messages, summaries, goals, handoff seeds or resume IDs. Context/history reads compose conversation scoping with independent-review visibility. Handoff files are indexed by role-session identity, without a project-wide fallback for a fresh session.

Messages, Tasks, Runs, calls, plans, discussions, timers, and followups retain their originating group. Configuration remains shared; setup proposals and role-prompt-change notices retain their initiating group, and older proposals derive it from their source Run or the default chat. CLI-switch handoff input and history-clear watermarks are group-scoped. Device/project/workspace capacity and terminal locks remain shared. The project-wide CLI-switch transaction rejects multiple unarchived native slots rather than merging their histories. Existing source-sync conflict handling stays project-wide/default-chat because its files are shared; no new cross-chat notification fanout is introduced.

The browser persists project and group selection together, with separate drafts, state-feed cursors and stale-response guards. Deleting the selected project recovers both selections together. Scheduled-job navigation loads the occurrence's group before opening its task. Sidebar execution highlighting follows the exact group; native-session history grouping includes project, group and role. No new periodic polling or idle model task is added.

`project-team-copy.mjs` freezes an allow-listed team/supervisor snapshot in `projectCopyOperations`, reserving stable destination and role IDs. The existing Worker `project_directory` query gains opt-in strict `creationOperationId` ownership and the `projectTeamCopy:1` capability. Exclusive directory creation rejects pre-existing unowned folders, including empty folders; a matching durable marker permits idempotent bootstrap repair. Missing or foreign ownership never triggers overwrite or recursive rollback. At most two device preparations run concurrently, verified receipts survive retries, and one transaction publishes bindings, independent role definitions and initial order only after every required device and runtime validates. Pending projects cannot dispatch. Copied roles retain exact prompt strings, including empty values; their copy marker exempts them from legacy preset reset during startup/language refresh. Global platform prompts remain global and are not snapshotted.

The only initial directory contents are the ownership marker, `AGENTS.md` and the `CLAUDE.md` pointer. No repositories, dependencies, old history, approvals, timers, synchronization state or account secrets are copied. Disabled-role devices are prepared only when later explicitly configured. The browser shows accepted snapshots and per-device progress, preserving the same request across reload/retry. See [the specification](design-parallel-conversations.md) for acceptance evidence and the distinction between local commits and deployment.

Browser state refresh remains single-flight. Each state GET has a 20-second deadline covering headers and body; timeout aborts the request and releases the refresh lock. Late responses cannot replace a recovered snapshot. Read failures invalidate the delta cursor so the next poll loads a full snapshot, preserving the displayed state and unsent drafts meanwhile. Focus, visible-page activation, page restoration and network recovery also request a refresh. Connection details show the last successful application of state, not merely an open event stream. Message submission and other writes are not automatically retried by this mechanism.

Home's steering barrier lookup uses `records_role_steering`, a project/role partial index over Tasks with non-null steering metadata. Each check rereads matching records and their current Run states; missing or unknown Runs remain blocking. Store startup adds the index to existing databases without rewriting history. `ProactiveFollowup.coveringRequest` reads project requests once per synchronous call, including completed child-result evidence, rather than once per active candidate. These changes reduce scheduler history materialization without a cross-turn cache, altered admission rules or reduced synchronization.

### Same-device CLI handoff

`RoleSwitches` persists one switch operation per role. `RoleSwitchRuntime` drains accepted work, records a source handoff, starts a separate staged native session and validates its acknowledgement. `RoleSwitchWorker` holds a durable role barrier, retires warm processes, checks native completion and compares Git/file metadata. Home atomically promotes the candidate and updates all fixed-supervisor records; queued execution waits for the Worker release receipt. Historical request snapshots remain unchanged, with a separate `executionBinding` for undispatched work (including dependency stages).

Both role editors use `public/role-switch.js`, with a renewable lease and authoritative cancellation/commit status. Full platform history is a hashed, role-specific artifact transferred through authenticated HTTP rather than a large WebSocket command. Candidate sessions are labelled staged, and maintenance is excluded from business reports and role calls. Codex maintenance uses a read-only sandbox; Grok maintenance exposes only `read_file`, denies prompting for additional tools and disables subagents/web tools. Business-run permissions are unchanged. Claude/Antigravity switching and older Workers are explicitly unsupported until validated. See [the handoff design](design-role-cli-switch.md) for cancellation and acceptance boundaries.

Role display names are stored user data and are never translated during routing. New unquoted unmentioned intake uses `project.supervisorRoleId`. A reply without explicit recipients resolves the saved agent's `roleId` or original Run identity before any legacy name fallback; an unavailable identity fails rather than changing the recipient. An explicit `targetRoleId` stays a direct dispatch even if an existing role has a name that collides with a broadcast keyword. New names cannot claim `all` or `everyone`. Shipped template names follow the same no-spaces validation as custom roles. Browser autocomplete and server mention parsing both recognize ASCII and full-width punctuation; this preserves message routing but is not a UI language-switching feature.

Fixed role, tool and supervisor rules are separated from the per-turn `executionRules`, and the latter and the new tool entry are sent in full each turn. The Home passes `task.runtimeInstructions` separately only to a Worker that declares `stableInstructions=1`; an old Worker still gets the full original format. The Worker's warm-process fingerprint includes the role name and the fixed rules, so changes of the temporary Run, the bridge and the report requirements no longer interrupt a warm process. Antigravity uses `event:user` streaming input and keeps the process alive after `result` (it needs a version that supports `--input-format stream-json`); Grok still cold-resumes. `instructionDelivery` lets Antigravity inherit the rules only from a successful earlier turn of the same project, node, role session and native ID; Claude records rule inheritance only when a warm process was truly reused, and the system configuration of Codex and Grok is always supplied in full. `sessionReuse`, `instructionFingerprint` and `instructionsInheritedFrom` are stored with the Run state.

`buildRunContext` stores the full snapshot and `inheritedContext`. `renderRunPrompt` only omits identical background fields or messages from a successful earlier turn of the original session, and never the current original instruction, explicit quote, delivery or execution boundary. Without evidence of successful delivery nothing is trimmed. Group-chat analysis remains an ordinary reply; the question of `wb call` and the receiver's result are separate linked records, and an `@` in model text does not dispatch.

The role form shows no permission, project directory or primary repository option, and internally uses `workspace-write` uniformly. It only selects the device, the actual CLI and model of that device, the reasoning effort and the prompt. When a directory is missing, the user goes to the single project-settings entry to prepare it. All repositories are fixed per Run. The old primary-repository association of roles is dropped in the startup migration, and historical Runs are not rewritten.

`src/runtime-probe.mjs` probes local CLIs: Codex uses a short-lived App Server to read authentication, the model catalog and rate limits; Grok and Antigravity read `--version` and `models`; Claude Code reads `--version` and `auth status`. Quota probes are best-effort per CLI. Codex account reads and Grok ACP billing do not create a Thread/session; Agy uses built-in `/usage` and `/credits`. Both Claude `/usage` paths receive a copied subprocess environment with `CLAUDE_CODE_SKIP_PROMPT_HISTORY=1`; that flag alone is not proof that a native transcript was suppressed. Each probe receives a fresh session UUID. After process closure, `claude-quota-history.mjs` locates only that UUID under configured/effective child history roots, rejects symlinks, oversized/malformed/mixed records and nonzero model usage, checks file identity and removes a verified pure-query file. Child environment inspection is scoped to the probe PID and never logged. Unknown roots or content do not authorize broader deletion; quota results are independent of cleanup. Normal conversation environments and historical records are unchanged by this automatic path. No probe submits a model turn. The Worker declares the `runtimeDiscovery` capability, probes at startup and every 5 minutes, and a manual `runtimes` query can refresh it; concurrent probes from one Worker are merged. A report contains only the version, whether authentication is ready, support flags, models and reasoning levels, quota where available, and the detection time. OpenCode is only detected by version, and anything without an adapter is not marked executable. Gemini is no longer probed, and the Home state snapshot also filters Gemini reports from old Worker caches.

The shared role quota renderer displays body-level hover/focus hints outside the clipped percentage glyphs; click/touch/keyboard activation opens a quota dialog instead of the role editor. It uses only that role's existing runtime/model quota and preserves the vendor's reset text and timezone rather than guessing from incomplete Claude date strings. Missing reset times are explicit. Hints are removed when their card detaches or the viewport scrolls/resizes; closing the dialog removes it. This UI does not refresh quotas, dispatch work or mutate role/session data.

`POST /api/workers/:id/runtimes` runs a probe on the chosen device, and `runtime_report` updates the Home mirror. Before saving a role the Home checks online status, a live probe, the actual directory and a matching model. Rooms and the Worker validate the model and CLI with the same `runtimeIssue` rules, and a probe older than 10 minutes waits for an update. Disabling an existing role can be done offline and keeps its configuration. Model selection does not use a global fixed list, models of different machines are not interchangeable, and a missing old model is not replaced silently.

A process-level probe failure (App Server exit, probe timeout, closed connection) is transient: the first one keeps the last good report of the same CLI version with its original `checkedAt` and a `probeWarning`, so the ten-minute `runtimeIssue` expiry still bounds staleness; the second consecutive failure reports the CLI unavailable. Failed probes retry after 30s, 60s, then every 120s through the single in-flight probe. Login, catalog and protocol errors are reported at once.

The refresh on the role bar merges the above detection per device and shows "detecting" and the result. A temporary network error, a query timeout or a 5xx is retried at most once, while an explicit authentication failure and 429 are not retried automatically. Only status queries are retried, and business tasks are never dispatched or resumed. An idle role card prefers a detection report newer than the last run failure; an older report cannot override a newer failure, and an expired report is not marked available. Executing, queued, awaiting reconciliation, approval, discussion waiting, launch blockage without a Run, and business verdicts that need handling keep their original priority. A failed manual detection is shown separately; the error, status and report of the original Run are fully kept. "Available" only means the no-reasoning probe passed and is not equal to a successful vendor model call.

Each project has one Room, and users do not fill in task forms. The underlying Task/Run records responsibility and run state, and `coordinationRequests` records cross-role calls. In a project with a configured supervisor, a new unquoted message with no `@` routes to that supervisor by ID; an explicit mention uses the exact stored role name (`@Supervisor` in a new English project). Without a configured supervisor, unmentioned text is discussion only. In all projects `@all` remains an announcement. Up to 4 explicit recipients dispatch directly as distinct role tasks, without a supervisor-only evaluation or inferred scheduling roster. Every target validates before the shared message/tasks commit; repeated aliases cannot create duplicate role tasks, and busy roles retain their normal queue. The browser Reply action prefills the saved agent sender only when there is no explicit mention, preserves the unsent body and removes only its own prefix on cancellation or changing the quoted message. Human quotations do not create an implicit task. Historical routing records are not rewritten. Ordinary agent output does not trigger dispatch. The built-in `wb` provides memory/docs, Git status, notes, call/wait/deliver, the supervisor's schedule, setup catalog/propose and role prompt. Repositories, new roles and device configuration are confirmed through cards, while the prompt of an existing worker role can be updated directly by the fixed supervisor. After a configuration card is confirmed only clone or binding an existing directory is supported, and there is no arbitrary pull/push/sync. The hand-off of an isolated execution is written to this Run's `.workbench`, and for an ordinary shared execution `LATEST.md` stays the index of the latest hand-off on that machine.

The project and the fixed supervisor configuration, the internal `systemSupervisor` role and the welcome message are stored together. The ordinary roles interface filters this internal role, and the supervisor is configured only in project settings. Worker roles are not created automatically and templates are only shortcuts for filling in. `src/role-templates.mjs` merges the shipped templates with user records in `roleTemplateRecords`: an unedited built-in follows the current language, an edited one keeps its saved text, a deleted built-in is hidden but restorable, and added templates use `custom-<uuid>` keys. Saves use an optimistic revision; role creation accepts only a currently visible template key, and existing roles keep their copied text. The legacy platform configuration assistant keeps its hidden system project, history and APIs for compatibility; the settings composer is replaced by read-only Configuration Information, which never dispatches assistant tasks. Account secrets do not enter version checks. The current implementation provides lightweight stage scheduling and does not include general plan revision, automatic repair loops or automatic cross-device pushes.

Restoring a built-in rechecks the current visible names before writing, so a same-named custom template cannot be silently duplicated or overwritten. Home localizes built-ins; the role picker and its prefilled fields use the returned template text verbatim. A template is an editable starting point, not a version-locked execution recipe: an already-open draft keeps its copied text, while newly opened forms see the current template catalogue.

Roles store a revision. An edit can carry the old revision to prevent overwriting, and requests and Tasks fix a `roleSnapshot`. Archiving keeps the role and history and is rejected while the role has unfinished tasks, Runs or calls.

`role-calls.mjs` manages persistent `coordinationRequests`. Notification, consultation and delegation remain distinct. A continuation is a new Run of the same owner/device with its existing call chain, workspace and native association; prior process/tool settlement and authorization gates still apply. Explicit waits persist original dependency IDs and a deadline (default 30 minutes, override 60 seconds–24 hours). Expiry records one event and can resume the parent without cancelling or replaying peers. The parent can wait on the same request again; late answers follow its current continuation. Transactions and stable continuation IDs prevent duplicate wakeups across deadline/reply/cancel races and Home restart. Pending unselected dependencies remain waitable after a selected subset completes. Paused/cancelled/steered tasks are not revived. The four-level/20-work-request limits exclude timeout continuation bookkeeping.

Rooms stamp a queued task with `blockedKind`/`blockedSince` only when it cannot start because its device is offline or its CLI is unusable; busy roles, capacity and workspace exclusivity are normal queueing. A waiter whose dependency stays blocked for ten minutes is woken once per blocked episode with `wakeReason: 'blocked'`, which behaves like an early timeout: the requests stay active, nothing is cancelled or redispatched, the episode is recorded as `blockedWake` on the child request, and a paused Home wakes nobody.

`wb report` in a discussion or asked Run returns `ignored` and writes no business report, and a Run that already has a report is rejected before the side effects of the ask transaction. The Home stop entry always calls `RoleCalls.stopRun`, saving the command, the exact `stopRunIds` and the state in one transaction. Retransmitting an old command does not rescan Tasks, and call cancellation still re-sends the original stop targets with `cancelRunIds` without unlocking early. Stopping a clarification only aborts the handling of the current question; the original Task is blocked and the question is kept, and the user can reply or resolve manually or stop the original task from the question card. If the consuming turn fails after resolve, the intent and the Task are blocked; after a safe cleanup, a web confirmation record bound to thread/`afterRunId` is required to continue the original Task once. The stop entry stays available while queued, and an immediate steering invalidates a blocked intent. Claude's native `thinking_delta` only produces a generic activity log at most once every 15 seconds, stores no thinking content and estimates no progress.

`git-delivery.mjs` provides workspaces at a fixed SHA, pushing and receive-side verification. A registered delivery is automatically approved, including older awaiting-approval records on the next schedule pass. It waits for source success and existing repository/credential checks, then pushes to `refs/heads/agent-delivery/<id>`; once ready, cross-node references are allowed. The publish result and the Worker outbox are saved atomically, and a crash during publishing marks it pending reconciliation without blindly re-pushing. The first batch requires the role to produce a Git commit first; automatic commits from a file list, main merges and deployment are not part of delivery. The protocol requires the Worker `coordinationVersion=1`.

A role stores the node, runtime, model, permission and Markdown instructions. The available choices are Codex, Grok Build, Antigravity and Claude Code that the node probed as supported and available. Every assignment fixes the role snapshot and injects the role instructions into this execution without overwriting the project's `AGENTS.md`. Changing a role affects only new messages; disabling a role pauses its queue, and operations already running need to be stopped separately.

Role templates separate collaborator-selection responsibility from execution text. The planning, execution, review and testing prompts remain empty, while Cross-Device prefills its execution instructions; editable shared supervisor defaults are maintained separately. Clearing saved execution prompts is an explicit operator action, not an automatic migration of custom role text. Existing histories and frozen run configurations remain unchanged, while later turns use the cleared components and the existing revocation-event mechanism.

The message `clientMessageId` is bound to its parameters, and the message and the internal dispatch to the recipient roles are committed in one synchronous SQLite transaction. Offline messages queue; the Home allocates by one active Run per role and node capacity, and starts only after the Worker finishes reconnect reconciliation and the runtime is available. An unstarted assignment can be cancelled; a process awaiting reconciliation blocks further dispatch on the same node.

A completion message is stored uniquely as `result-runId`, linked to the Run's terminal state and the source message. Retransmitted events and Home restarts do not post to the chat twice. Token and tool output goes only into the details, and the group chat loads the most recent page after an increment via the Room revision, without re-reading history on every token. Messages are 60 per page, and drafts and unconfirmed sends are stored per project in the browser session.

A successful turn that registered `wb wait` for its own handoffs (`RoleCalls.wait` records `run.handoffWait`) and has no explicit business report does not publish an extra completion message: the handoff cards already show the work. The turn itself adds nothing to the conversation while it waits: the chat's queue lists the wait ("waiting for results from @roles") at the slot its result-driven or timeout continuation will run in, and the reply stays in the Run details. Explicit `passed`, `failed`, `blocked` and `needs_input` reports bypass this handoff suppression; existing publication rules and question wording remain in force. Execution failures and stops are still published, and the continuation's result replies normally.

Quoted context is limited to 8000 characters and the whole group history is not injected. A same-role reply is conversation context, including replies about failed executions, and does not itself request Git delivery. Informational discussion quotations do not transfer a Git workspace. Cross-role Run quotations retain the existing completed-source/workspace checks: a same-node peer gets the source reference, while a cross-node peer requires exactly one `ready` Git delivery and carries its `deliveryId`. Source/delivery/coordination metadata is assigned per recipient; it is never attached to the original sender or supervisor merely because another recipient needs it. All required transfer checks occur before creating any task. With no delivery or several ambiguous deliveries the whole request refuses and explains. These quote rules do not weaken fixed-version execution-plan gates.

The discussion-specific reply action keeps its original question/version/session binding and sends plain answers to the asker without inserting mention text. An explicit mention in that draft selects ordinary Room dispatch instead and does not silently answer or resolve the original thread. User edits to an automatic reply prefix relinquish prefix ownership, so cancelling a quote cannot remove a manually retyped recipient. Discussion display tolerates message-first/thread-later loading without treating two missing IDs as a matched blocked task.

## Execution and state

Report submission has a durable receipt bound to Run, submission ID and normalized content. The report, Run projection and receipt commit atomically. Same-ID replay returns its original revision without overwriting a later verdict; identical content derives the same ID, while an explicit new ID allows a deliberate revision. After a transport timeout the shared `wb` client queries the receipt, retries at most once only when a compatible Home confirms it is absent, and reuses the same ID. Unavailable confirmation returns `pending_confirmation`, never an invented failure verdict. `wb report status ID` reads receipts, including settled Runs when their bridge remains available; it does not reopen execution or permit new terminal-state reports. Legacy saved reports can be recognized by matching content without rewriting their revision. Older Homes that lack confirmation support are not automatically retried.

The terminal event's event/Run update, the RoleCalls wrap-up and the Room result message are committed in the same Home SQLite transaction, and the ACK is sent only after the commit. On startup the terminal wrap-up is replayed to repair old crash windows, and existing terminal business verdicts are not recomputed. A cancel request or a cancelled plan is not continued automatically. When startup validation rejects, the Task and the corresponding unstarted Call are closed together, so no queued call without an execution can block a plan or scheduled job.

A Codex pipe error only fails the current session or marks it pending reconciliation and does not bubble up to terminate the whole Worker; a closed RPC connection is rejected immediately. A managed process that ended normally or failed to start gets SIGTERM first and SIGKILL if still alive after 3 seconds; this must not be used to mark active tool results as successful. Front-end file preview and the desktop link isolate stale responses by request generation, and paged history text shares an in-flight request serially per view state so that copying does not repeat segments.

A Project stores the collaboration identity and a stable `folderName`; `repositories` identify a repository by `projectId + key`, and `repositoryWorkspaces` bind a directory by `repositoryId + nodeId`. A Run fixes `projectRoot` and the full set of repositories, a missing working repository blocks the start, and the supervisor can still help complete the configuration. `project-delivery.mjs` publishes and receives per repository SHA, and the receiver generates a set of fixed-commit directories in the project. Uncommitted files are not synchronized, the original branch is not switched, and atomic multi-repository commits are not promised.

Explicit review deliveries persist immutable `purpose: review` through `/api/agent/deliveries/review`. The separate endpoint fails closed on older Homes; publication, direct reception and execution-input fetch require `reviewDeliveries: 1` on the participating Worker. Review uses the dedicated ref even for unchanged items and skips only project-baseline publication/advancement. Current owner, source success, clean source, repository/ref/SHA, occupancy and non-force protections remain. Direct review handoffs create an isolated role-session key within the same visible group; continuations retain its key and workspace, leaving the original native session and history intact. Legacy/ordinary development deliveries keep baseline advancement and fingerprint compatibility. See [design-review-delivery](design-review-delivery.md) for verification boundaries.

`setupProposals` are proposed only by the current project supervisor's Run. Repository proposals retain `baseBranch` but omit the retired `baseCommit` and `publishBaseline` setup fields; existing proposals with those fields remain confirmable, and saved repository metadata is preserved. A fixed entry outside the chat scroll area shows the selected project's pending count and opens its configuration cards in a dialog; reading or closing that dialog does not approve anything. After web confirmation the repository and role actions run in order and each result is recorded; confirming again returns the existing state. The Worker's `setupOperations` records results by operation ID, and a failure, restart or timeout requires verification and is not overwritten or redone automatically. Successful configuration results enter the group chat and are read by the supervisor on the next turn. The model is a trusted-operator one, and the tool allow-list is not complete isolation against a malicious shell on the same account. Above the chat, the project shows only suggestions that are pending, running or blocked (`OPEN_SETUP` in `public/project-setup.js`); configured and rejected ones are history and no longer take room there.

`wb role prompt` goes through a separate agent bridge allow-list and Worker credential and accepts only an active Run of the fixed supervisor of the current project. The Home verifies the role ID, the current revision and a stable request ID, and within a transaction updates only `instructions` and the revision of a non-system worker role. A retry with the same ID returns the original result, and a conflicting ID or stale revision is rejected. `rolePromptChanges` keeps the text before and after, the source Run and the time, and the project group chat receives a version summary. Generated Tasks and Runs keep the original role snapshot, and only later new messages use the new version. Deleting a project cleans up the audit records too.

A new dispatch must have a node binding. When creating a Run, `localRoot` is fixed as `projectRoot`. Delivery and command retransmission use that snapshot, and configuration changes do not affect existing Runs. The Worker checks the path again before starting. An old Run without a snapshot keeps the original project path, and a new dispatch of an old project must first add a binding. The Worker declares support for path queries through `capabilities.workspaceBindings`.

Worker registration also reports `nodeKind: local | cloud` and optionally the legacy `remoteDesktopUrl`. An explicit `NODE_KIND` wins; by default Linux is recognized as cloud and other platforms as local. The Home only stores and mirrors this fact, and the UI uses it to choose local or cloud-server icons and text instead of guessing from the device name. A legacy link may only be `rdp://` or `http(s)://`, and script protocols, overlong values and password or token parameters are rejected. On a macOS Home, the bottom-left and the device card share a remote-desktop entry: it first probes the remote loopback xrdp port with the SSH key of a registered device, then establishes a separate local `-L` tunnel and finally starts the Windows App client; the user then clicks the connection saved in the client and reuses its login credentials. The page gives feedback per stage but never reports "client started" as "desktop logged in". No new `.rdp` connection is generated, the Worker's reverse tunnel is not modified, and the client login screen is not operated automatically. A Linux Home hides this macOS-specific shortcut.

If the configured local desktop port is already listening, macOS process inspection can reuse a same-user SSH forward only when its explicit loopback mapping, registered SSH destination and established connection match. Conflicting same-port declarations are rejected. The external process is revalidated before client launch; its record is discarded on configuration change or Home exit without terminating it, so any other forwards it carries remain intact. Unknown listeners and failed inspection stay blocked. This is a trusted-operator compatibility check, not an isolation boundary against malicious processes on the same account.

When a system `/usr/bin/nc` ProxyCommand holds the SSH socket, reuse additionally verifies a unique direct child, its parent/user identity, explicit registered IP/port arguments and established destination. Child and SSH start-time/command identities and listener ownership are rechecked before returning the original SSH PID. Hostname-only or arbitrary proxy chains are not newly accepted by this fallback. No process is signalled or replaced during inspection.

Creating a task only stores the requirement. When execution starts, a transaction checks the `commandId` and whether the current Task already has an unfinished Run, creates a stable Run and then dispatches. The Worker writes the command and the Run to its local database before starting the process. Network retransmission reuses the command ID. File and path queries are bound to the target node and fail immediately when disconnected.

Worker events have their own ID and a per-Run `seq` and are stored locally as pending first. The Home persists and de-duplicates before acknowledging. An old sequence number does not overwrite new state, and events of an old Run do not modify the Task of a new Run.

A stop request records `stopping`, and only an `interrupted` from a real `turn/completed` is a normal stop confirmation. When the App Server exits abnormally while a turn is active, the state is kept pending reconciliation so a tool is not wrongly assumed stopped. A Worker restart only reconciles the recorded processes and does not restore external sessions.

The legacy manual confirmation only applies to the latest successful Run. The group chat shows execution completion and the role's verdict and does not claim business acceptance automatically. A user can currently quote a delivery to let an independent role review it, but a fixed-commit Review entity, automatic review forwarding and automatic Git merging are not implemented.

## Native permissions

Codex uses `thread/start`, `turn/start` and `turn/interrupt` of the App Server. The sandbox is uniformly `workspace-write` and `approvalPolicy` is uniformly `never`; the workspace is created and restricted by the Worker beforehand. Both new and resumed sessions explicitly enable the network to support Git and cross-device communication. The extra writable scope only adds the current directory and the git-dir and git-common-dir that Git resolves for bound repositories, so that fetch and commit in a worktree are not blocked by read-only metadata, and the whole user directory is not opened. Git hosting authentication still has to be configured separately, and network access does not mean repository access exists.

The protocol reference is the Codex App Server documentation. The sandbox enumeration in an online documentation example once differed from the installed version and was corrected to the real interface response, so it must be verified again whenever the runtime is upgraded.

Codex, Grok, Antigravity and Claude Code all auto-approve tool calls inside the project workspace assigned by the Worker. Claude Code uses `--dangerously-skip-permissions`, Grok uses `--always-approve --permission-mode bypassPermissions --no-plan`, and Antigravity uses `--dangerously-skip-permissions --mode accept-edits`. The page does not wait for per-step approval for these runtimes; interactions of unknown runtimes are still rejected and recorded.

Each execution inherits the node's native CLI login and user configuration, and global Skill/MCP instructions are not isolated separately. The related context counts toward runtime usage; the UI shows total input and cached input and does not treat cumulative input as uncached billing.

## Current limitations

### Retired collaboration session queue

The `schedule`, `collaboration` and `pass` CLI commands, capabilities, help and agent routes are removed. The bridge rejects these endpoints. Browser collaboration mutation endpoints return 410 except POST release/close for an existing same-project session. These two human-only queue controls preserve explicit review release (also after close); closing alone does not release protected opinions. GET history stays available; collection, membership, linking, budget and configuration writes remain disabled. New work uses `wb task` and `wb call`. Exact preceding EN/ZH platform/supervisor prompt hashes migrate to the task-aware defaults; custom and explicitly empty templates stay unchanged.

At Home startup `SessionQueue.retire()` disables the project feature flags and closes collectors. Definitely unsent reserved batches are released through the existing cancellation path (including unstarted tasks and reserved budget). Attempted deliveries, pending verifications and running batches remain attached to their original Runs/Workers; their existing verification and finish paths still run and never redispatch into the disabled queue. Records, results and review protection are retained, not fabricated as successfully processed. Protected review history is not automatically released. This is not the later RoleDiscussions/discussionIntents cleanup; those records and compatibility paths are unchanged.

The following protocol describes retained batches only; no new session or batch is admitted via Home. `collaboration-sessions.mjs` still owns historical membership and review visibility; `session-queue.mjs` retains receipts, collectors, batches and cycles.

Home reserves capacity and budget. Worker protocol 2 rechecks the actual native-input boundary, and native acceptance charges once. Verified non-delivery refunds; unknown delivery stays linked to the original Worker/Run for verification, without redispatch. Known startup failures block repeated attempts until relevant facts change. Old Workers cannot consume new batches or protected-review inputs.

New automatic consultations and clarifications inherit the same cycle. Answers and necessary resumption of accepted work do not charge again. The original batch survives call/wait and discussion/reply/resolve through `continuationBatchId` and its effective Run binding. Native output remains private; pass and explicit publication are validated separately, and a generic note cannot satisfy pending addressed requests.

The review-bound store filters before paging, summaries and input assembly, traversing request/Run/Task provenance and child topics. Removed reviewers remain protected until release. Managed documents compare server-captured hashes to actual Worker files and use role-private handoffs with canonical paths. This does not sandbox arbitrary native shell reads, detect unlinked paraphrases or erase previously seen content. See [V3 acceptance](design/session-queue-v3-acceptance.md) for measured scope and remaining drill limits.

### General limitations

- The current state is a development-grade managed execution. Multi-user permissions, per-device revocation, Project Epoch and manual primary/standby switching are not implemented. The default listener stays on loopback.
- Not implemented: automatic AI supervisor decomposition and forwarding beyond the lightweight stage scheduling, multi-user identities, other ACP runtimes, Feishu. Automatic recovery of native sessions has not been verified for every CLI on two devices; Grok, Antigravity and Claude Code have no native per-step approval comparable to Codex.
- Data is persisted on a single Home with no cross-host replication.
- File preview allows only ordinary text files inside the currently registered workspace, with limits on size and traversal depth; it is not a full project file manager.
- An unknown run of the same task cannot be retried automatically; the original process needs manual verification.
- SSH onboarding requires Node.js 22.16+, npm and Git on the remote machine. The background Worker is supervised but no boot service is installed. Installing a CLI does not do the native login for the user.
- GitHub/Gitee account and repository-creation interfaces are covered by simulated-response tests; authenticated creation needs a user token to verify. Creating a repository after an external API timeout needs verification and is not repeated automatically.
- Token statistics cover the CLI history that a device's local `ccusage` can recognize. They are not a vendor bill or the remaining account quota, and a device without local history shows 0. A single range covers at most 366 days.

These limitations stay visible, and simulated events, fake online status or static cards are never used in place of real capabilities.

### Group-call simplification compatibility

Whole-task transfer moves ownership without making the recipient a child call. The receiver arranges review and returns the final reply. Role reminders and short wait IDs share the existing call infrastructure. Managed results use final replies instead of `wb report`; a successful execution is not a business acceptance verdict. New stage plans cannot contain migration, deployment or production operations. Before releasing waiting dependencies, the same restriction is checked on persisted older plans, including stages marked running before their requests were dispatched; already-running requests are not cancelled. A blocked irreversible step must be reviewed and assigned separately.

The group Roles sidebar keeps the existing clickable project-folder/device entries above the roles and does not enumerate local project files on tab selection or background refresh. Folder contents use the existing explicit action. Recent run outputs retain their separate bounded view.

Path recognition in message text stays linear in the text: media paths (`mediaPathMatches`) and inline document paths (`documentPathAt` in `markdown.js`) are matched only within a word (a run without stop characters) that ends in a matching extension and is no longer than a real path, and the side-preview decorator skips text with no document extension. Unanchored over a long base64 word with many `/`, the old patterns backtracked quadratically: a chat of evidence parts froze the page for seconds on every redraw. Results are otherwise unchanged.

`public/side-preview.js` owns one document controller for Sessions and group chat. ### Home-only conversation tasks

Role-side task tools always read the current Home record. No timer, task scheduler, task-based heartbeat or command removal is added.

### Simple metadata directory synchronization (S1)

An explicitly previewed `detection: 'metadata'` scope requires exactly two capable Workers (`sourceSyncMetadataMode:1`) and the existing display Mac. Revision, generation, binding and scope-policy fences remain in `SourceSync`; absent detection retains the hash engine. `source-sync-metadata.mjs` defines a separate metadata schema and portable path validation. `source-sync-metadata-home.mjs` plans within existing batches/commands; there is no new scheduler. `source-sync-metadata-files.mjs` supplies stat-only observations, stable selected-file reads and guarded journaled application.

Home stores `sourceSyncMetadataScopes` (root identity per endpoint/generation) and indexed `sourceSyncMetadataBaselines` (project, scope, generation, path, per-device existence/mtimeNs string/size/identity, revision, operation ID, acknowledgement time). The empty compatibility hash manifest supplies conflict scope information only; metadata never enters hash entries. Unknown initial pairs and paths with old deletion history are pending, not assumed equal. S2 provides explicitly confirmed, paginated initialization (below). Changes are relative to each endpoint's own baseline, not clock ordering across devices. No-change captures do not read business bytes; periodic observation stays metadata-only at five minutes, or thirty seconds with incomplete watches, retaining the existing quiet window/backoff. Metadata scopes do not enable the old per-run whole-content provenance scan.

The existing authenticated HTTP transport carries capture metadata, selected read receipts and file bytes. Dual edits first exchange hashes; only divergent versions are staged at Home and promoted to conflict storage before committing conflict references. Equal versions only advance both baselines. Normal transfer hashes are integrity checks during the single source-byte read, not change detection. Targets wait behind managed work, recheck expected attributes and inode identity, fsync temporary content, displace into a short recovery sibling, install without clobbering an intervening writer, and report their own actual attributes. Durable command results replay without reapplying; prepared journals recover only exact saved inode evidence. Uncertain or conflicting recovery retains evidence and never reports success. Metadata batch retirement includes blocked/cancelled batches: an indexed scan of at most 32 batches per tick reuses cleanup commands and persists `metadataCleanedAt` only after Worker confirmations and Home namespace/quota cleanup. Worker guards retain staging during in-flight transfers, reconciling commands or preparing/prepared journals; cleanup retries after a definite recovery outcome and survives restart. Only applied journal siblings are removed; shared conflict blobs remain untouched.

Metadata transfer blobs use per-batch namespaces on both Home and Worker, separate from legacy/shared content. After all apply receipts, existing cleanup commands remove confirmed private siblings and batch staging. Home deletes its namespace only after those acknowledgements; late uploads cannot recreate cleaned data. Unresolved conflict versions and legacy blobs remain referenced in the shared store. Terminal batches reclaim dedicated staging after Worker cleanup acknowledgements; only uncertain journals or reconciling commands defer reclamation; shared GC remains reference-guarded and audit expiration is handled separately by S3. Metadata conflicts do not auto-dispatch a repair or supervisor model. Existing explicit human assignment and reviewed-candidate acceptance remain available, with fresh per-path evidence before distribution. File status labels its confirmation as `metadata_and_receipts` and returns no invented content hash. Actual process-level Mac testing and resource measurement remain separate acceptance gates.

### Metadata baseline initialization (S2)

`SourceSyncInitialization` is called from the existing Home tick. Browser-only `pending` (GET), `initializations` (GET/POST), and `initializations/:id/resume` routes require the current metadata configuration. Start requires a stable request ID, configuration revision, a scope, selected paths or all-pending, an operation and explicit confirmation. Resume also requires explicit confirmation, the current configuration revision and a stable request ID; `sourceSyncInitializationResumes` makes retries idempotent, including after another pause. The UI asks again before resuming. The UI shows both endpoints’ exact nanosecond metadata without asserting different content, pages 50 paths, and asks for confirmation before sending. All-pending freezes a database row watermark, so later discoveries are not silently included. Neither model tools nor periodic watchers start initialization.

Home stores `sourceSyncInitializations` separately from audit logs: generation, authorization, cursor, current batch ID, processed count and retry attempt survive restart. Existing scheduling serializes one batch at a time; each contains at most 100 selected paths and 100 MiB combined observed bytes, additionally checked against fresh captures and existing file/path limits. Scope/path queries use `records_metadata_scope`; active jobs and resolved cleanup candidates explicitly select their partial indexes with `INDEXED BY`, in bounded cursor pages (8 jobs or 16 conflicts per tick). Blocked/cancelled jobs pause; explicit resume waits for definite results and safe staging cleanup before a new attempt. Successfully baselined paths are skipped. Uncertain journals prevent resumption. This is operation recovery, not S3 audit retention.

Verification uses stable per-path reads on both Workers and compares their content digests; equal content establishes each endpoint’s observed baseline without file upload/apply. Unequal content is staged and copied into shared conflict storage; originals remain unchanged. Overwrite always preserves both existing versions before generating an apply command; current metadata/identity checks and durable journals remain S1’s. Equal content needs no rewrite. Initial-copy protection is represented as an `initializing` metadata conflict; confirmed application resolves it, while a changed target retains the copies and requires human action. A cancelled, definitively retired initialization may recheck its own protection record on explicit retry; it cannot bypass unrelated unresolved conflicts. There is deliberately no reuse of legacy consistency evidence.

Metadata conflicts also offer a browser-only, explicitly confirmed choice of a saved side. Resolution recaptures both endpoints and rejects changed evidence before application. Cleanup considers only resolved metadata conflicts whose resolution batch has all receipts and private cleanup ACKs. Shared blob deletion runs the reference check, unlink and quota update without an async gap in one transaction, excluding in-flight storage writers. Indexed project/kind SQL searches retain references from other unresolved conflicts, legacy conflict history, legacy manifests, uploaded captures and unaccepted receipts, device manifests, immutable versions, candidates, unfinished batches and pending/recovering commands. Resolved, fully retired metadata conflicts do not mutually pin the same hash forever. Metadata conflict history is audit-only and does not pin bytes; legacy history and versions still protect content, and no history rows are deleted. A retained candidate stores its check time and next check time, deferring expensive reference scans for one hour, including across Home restart. A new conflict generation clears that delay and carries forward unreleased prior entries in `pendingCopyEntries`, retaining ownership until the new conflict is resolved and safe to clean. Cleanup is retried in bounded pages after restart; unresolved conflicts are never candidates. S3 audit records and retention are described below.

### Metadata sync audit and retention (S3)

`SourceSyncAudit` records only metadata-mode operations after per-file planning; unchanged observations and pending-baseline previews emit no rows. `prepare`, validated read/stage/apply receipts (including waits, blocks and cancellation), and terminal staging cleanup call the audit observer. File success requires an applied receipt or actual equality verification, not CLI/run state. Each row contains record/operation/attempt IDs, project/scope/path, endpoints, action, Home start/finish times, metadata before/confirmed after, phase/reason, comparison hashes, conflict/retry links, payload bytes and duration. Ordinary transfer checksums and overwrite-preservation checksums are not advertised as content verification hashes. Unconfirmed after-metadata stays null; a failed/cancelled operation can still report a late applied receipt without claiming rollback. Audit is never used to decide whether to apply a file.

`sourceSyncAuditStates` retains compact per-batch/path replay identity, signature digest and byte counters, independently of the expiring `sourceSyncAudit` rows; `sourceSyncAuditHeads` retains the latest lineage per project/scope/generation/path. The next attempt after a failed attempt shares operationId, increments attempt and links retryOf; a successful lineage is closed. A timeout/retransmitted command is the same attempt, not a new row. Audit deletion cannot cancel or repeat an apply. HTTP payload counters count upload and download bytes once per request, including partial received payloads; headers/TLS framing are excluded, and deduplicated blobs are attributed to the first matching path in that command. No chunk creates a row or refreshes retention.

Home clock is injectable. Terminal rows expire after 30×24 hours from finishedAt; active rows from the last actual stage/signature change. Byte counters and repeated unchanged receipts do not refresh the clock. If an active row expires, a later real transition creates a new recordId under the same operationId/attempt. List/detail queries hide expired rows immediately. Existing tick runs a durable daily sweep with a frozen cutoff, deleting at most 100 audit rows per invocation through `records_sync_audit_expiry`; an interrupted sweep resumes after restart. The same sweep additionally examines at most 100 terminal replay identities older than 30 days through records_sync_audit_state_finish, with a persisted cursor. Identities whose batch or commands remain unfinished are retained until a later daily sweep. Heads are removed only when still pointing at the reclaimed identity, through records_sync_audit_head_state. Live identities, operations, files, baselines, config and unresolved conflicts are protected. Explicit project deletion removes audit rows, states, heads and initialization jobs/resume keys. Command paths, receipt files, conflicts and pending paths are indexed once per observe; matching is linear in operation and path entries. One observe shares one transaction (or the caller transaction); unchanged signatures perform no writes or per-file transactions.

Browser-only `GET source-sync/audit` accepts exact `path`, either-end `device`, `status` (syncing/succeeded/failed), ISO `from`/`to`, and opaque `after`. It returns `{items,next}` with 50 rows, newest Home recordedAt/id first. Project, path, source, target, status and operation indexes support bounded keyset pages; device queries merge at most two 51-row pages. `GET audit/:recordId` returns the scoped record and a paginated retry chain (`after` pages that chain). Expired links may be unavailable. These endpoints read metadata only, not file bodies or all logs. `GET initializations` now also returns `{items,next}` using a project/createdAt/id index; the ordinary status response no longer includes a truncated initialization array. UI opens these lists on demand inside project sync settings without adding a timer or changing the group-chat layout.

`.worktrees` is a mandatory sync exclusion again (`excludedSourcePath`): the platform's `run-*` folders, the retired project baselines and any worktree a role created by hand all stay on their device. Role-created worktrees had been synchronized as plain folders for a few days; on a real project they made up 99% of the manifest and saturated the Home tunnel, and the copies had no `.git` to work in. At startup Home drops stored manifest, device-acknowledgement and metadata-baseline entries whose paths are excluded under the stored scope policy (`SourceSync.dropExcludedEntries`), recomputing the canonical digest and revision, and cancels open conflicts on such paths together with their unstarted repair tasks; without that, a project that had synchronized a worktree would fence every later batch on `source_scope_changed` or fail digest validation of its own stored manifest. Entries leave the records only; no deletion is sent to any device. Pending commands from before the start that still name such paths block their batch with `source_scope_changed` (once at start and on each receipt), so they are reconciled but never redispatched; receipts skip excluded paths, and a cancelled conflict stays cancelled through later resolution outcomes. The default platform prompt now tells roles to work in the shared bound folder, not to create worktrees, and not to switch branches, stash, reset, clean or stage other people's files there; cross-device sharing of committed work goes through Git delivery. It also forbids carrying files, logs or bulk data (such as base64 in parts) in the chat, `wb note` or call text: material for another device goes through the sync-scoped `.workbench/docs` or `wb deliver`, and material outside the sync scope is reported (device and path) for the user to decide.

Native page polling allows one outstanding read for the current session generation. Switching sessions and confirming a send invalidate only the appropriate read; a late send response from another session cannot invalidate the current session. Copy-feedback timers belong to their rendered buttons, so an unused candidate node cannot cancel the visible button's three-second reset.

A failed service-worker precache removes its incomplete cache. An explicit update reload unregisters the current scope when Home advertises a different build, then the newly loaded page registers its service worker again; a cache name alone is not proof that installation completed.

A retiring capture can expose a hash proof of the manifest bundle already stored by Home. Cancellation compares that proof with the Worker's immutable saved result and sends only its compact receipt when they match; missing or mismatched proof falls back to the original upload. Active captures without an accepted result still withhold this proof so required file uploads cannot be skipped.
