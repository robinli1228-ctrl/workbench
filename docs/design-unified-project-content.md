# 双设备简单自动同步与30天记录需求

日期：2026-10-26（Asia/Taipei）
状态：**用户已确认简单方案；本详细文档待审阅，未改代码、配置或线上数据。**

## 1. 本次目标和边界

Mac 与服务器对应项目目录中的已保存文件自动同步。平时只比较文件修改时间和大小；只有发现双方都修改过同一文件时，才计算内容哈希判断是否真正分歧。正常同步不保留目标旧文件副本，发生内容冲突时保留双方。逐文件同步记录保留最近30天，过期自动清理，方便反查。

本稿依据用户最新决定，**替换本文件此前的“统一项目内容与自动交接”大方案**。旧稿留在Git历史中，不再作为本轮实施依据。自动准备审核交付、未提交任务快照、四CLI共识验收和完整产物管理均不属于本轮。

本轮只改变文件同步的判断、冲突副本和审计记录策略；不改派工、审核顺序、任务列表、模型、历史消息或Git交付权限。保留既有连接和活动任务，不以关闭同步降低资源消耗。

### 1.1 已选方案

| 方案 | 决定 |
| --- | --- |
| 每次检查都完整读取文件计算哈希 | 不采用，普通检查成本过高 |
| 比较时间和大小，双方都改时才核对哈希 | **用户选择** |
| 无条件采用两台设备中时间更晚的文件 | 不采用，时钟差异和并行修改会造成覆盖 |

复用现有 [文件同步协议](design-source-sync.md) 的范围、连接、接收、权限和任务占用保护。本稿规定的简单模式在获准启用的范围内替换旧的内容哈希变化判定、正常旧版本保留和本轮日志保留策略；未迁移项目和正式Git交付保持原行为。不要把两种判断同时运行，也不要另建同步调度器。

## 2. 核心规则

1. 每个文件记录**上次成功同步后，两端各自的修改时间和大小**。
2. 下一次检查时，分别与该端自己的上次记录比较，不比较两台机器谁的时间更大。
3. 一端变化、另一端没变化：自动向未变化端同步，正常替换后不留旧副本。
4. 两端都有变化：先计算双方哈希；相同则确认一致，不传文件、不留副本；不同则保留双方并记冲突。
5. 同步成功必须收到目标端完成写入的确认；发送出去不等于成功。
6. 只记录实际同步、失败和冲突处理，不为每次无变化检查生成日志。
7. 日志最多保存30天；当前同步基线、正在执行的操作和未解决冲突所需数据不是过期日志，不能一并删除。

## 3. 文件范围

- 只处理明确绑定且已启用同步的项目、仓库或共享文档范围。不同设备绝对路径可以不同，以项目/范围/相对路径识别同一个文件。
- 源码、项目规则文件、文档、图片和附件只要在已授权范围且满足现有策略，即可同步；不因为扩展名是PNG而额外排除。
- 继续排除Git元数据、依赖目录、登录凭据、数据库、平台运行状态、桥接文件及其他现有强制排除项；不直接镜像整个分区。
- 沿用现有文件大小、批次大小、路径安全和磁盘容量限制。超限、软链接、跨项目路径等须说明原因，不能称已同步。
- `.worktrees` 内的临时产物不会因此自动纳入。截图放在未授权路径、历史链接映射错误仍需另行修复；本需求不能宣称解决所有文件打开错误。
- 未开启同步的项目保持关闭。首次启用或扩大范围须展示实际目录、包含/排除清单和预计覆盖影响，不先上传新增范围的内容。

## 4. 上次同步记录与变化判定

### 4.1 当前基线（小量状态，不是文件备份）

每个参与同步的文件至少保存：

| 字段 | 含义 |
| --- | --- |
| projectId / scopeId / relativePath | 项目、仓库或共享范围、相对路径 |
| bindingRevision / policyRevision | 防止换目录或范围后误用旧记录 |
| deviceA / deviceB | 同步双方身份 |
| A.exists / A.mtime / A.size | A端上次成功确认后的存在状态、修改时间和字节数 |
| B.exists / B.mtime / B.size | B端对应状态，允许与A端时间不同 |
| revision / lastOperationId | 平台确认顺序与操作身份，不代表Git提交 |
| acknowledgedAt | 最近一次确认一致的时间 |

修改时间存储使用文件系统能提供的精度，不先截断到秒，也不把大整数时间转换成丢精度的浮点数；页面可显示到毫秒。文件是否仍属于同一绑定、类型和身份的检查属于安全保护，不是额外内容哈希判断。

**两端修改时间不要求相同。** 接收端写入可能产生自己的时间；成功后读回两端实际属性分别保存，不能拿源端时间当目标端基线，避免同步后的写入通知触发往返复制。

### 4.2 判定表

“变了”指相对于该设备自己的上次成功基线，存在状态、修改时间或大小变化。

| A端 | B端 | 处理 |
| --- | --- | --- |
| 未变化 | 未变化 | 跳过，不读正文、不计算哈希、不新建日志 |
| 变化 | 未变化 | A→B，写入前重新核验B，正常同步不留旧副本 |
| 未变化 | 变化 | B→A，同上 |
| 变化 | 变化，且都存在 | 核对双方哈希，见第6节 |
| 删除 | 未变化且存在 | 传播A的删除；反向情况同理 |
| 删除 | 修改且存在 | 删除/修改冲突，保留尚存内容，不再盲目删除 |
| 删除 | 删除 | 确认双方均不存在，更新基线，不复制文件 |

修改时间相同但大小不同，也算变化；时间变了而大小相同，也算变化。单端原样保存可能产生一次多余传输，接受这个取舍，不为了省一次传输对每次单端变化计算哈希。

### 4.3 第一次同步与无法证明的基线

- 两端都不存在：没有可同步文件。
- 只有一端存在、且不存在“另一端曾删除”的历史：可作为新增同步。
- 两端都存在但没有可信共同基线：不能假定只有一边修改，也不能直接按时间覆盖。显示“待建立同步基线”，先预览双方元数据与覆盖范围。默认保留双方现状，不自动写入；若用户明确选定一端覆盖初始化，先把双方视为“初始版本可能分歧”，按第6节冲突存储保全这两份现有字节，再执行获准覆盖，待双方应用并确认基线后清理无引用副本。这是无基线时的一次性保护，不是日常正常同步备份；保全过程失败则不覆盖。未核内容时只称可能分歧，不伪造哈希或断言内容不同。
- 可复用旧系统已确认的一致性证据，但必须证明当前绑定和当前文件仍对应那次确认；不能仅读取当前mtime就宣称旧基线有效。
- 仅凭元数据无法判明初始两份内容是否一致。若需要逐字节确认首次基线，应单列一次性初始化核验并明确授权，不暗中加入周期性或所有文件的哈希扫描。
- 从断线、旧状态、清理记录或未知操作中恢复时，缺少基线按同一原则处理，不把“查不到”当成未变化。

本节是启用/迁移前置，不要求日常每次同步由用户选择。

## 5. 何时检查、如何正常同步

### 5.1 触发方式

- 继续以操作系统文件变化通知为主，沿用现有约0.5秒安静窗口、连续变化约2秒触发检查的合并机制。
- 通知明确时只检查相关文件属性。新增、删除或目录变化无法确定具体文件时，对受影响范围遍历元数据。
- 正常监听保留每5分钟元数据兜底；监听不完整时保留每30秒元数据兜底，并沿用已有失败退避和资源让路。
- **本简单模式不做周期性的完整内容哈希核对。** 此项与旧模式不同，是遵从“只有双方都改才核对哈希”的明确取舍；旧模式未迁移范围不受影响。
- 内部定时器检查是否到期，不等于每次都扫描目录。浏览器刷新和模型每条输出不能触发全目录扫描。

### 5.2 正常新增/修改

1. 根据双方基线确认只有一端变化，记录本次源属性和目标预期属性。
2. 目标正被活动任务使用时不覆盖，保留待同步状态，等安全应用时机。其他无关范围可继续。
3. 通过既有认证通道传输文件；可使用短期接收临时文件，**它是新内容的暂存，不是目标旧文件备份**。
4. 传输前后检查源文件仍稳定；写入前再检查目标是否仍与预期属性/身份一致。任一变化则本次不覆盖，重新判断。
5. 接收完整字节数、完成写入并进行现有文件系统持久化/原子替换，记录目标实际属性和操作回执。
6. 确认成功后更新双方基线，保留同步日志，清除本次不再被使用的新内容暂存。

普通路径不新增源/目标文件SHA256读取，也不把旧哈希缓存当作本次内容已验证。日志的确认方式应为“元数据与完成回执”，不是“内容哈希一致”。现有网络认证与传输完整性保护保留；“不计算内容哈希”不等于允许截断传输或半文件落盘。

正常传输中的中断、超时、写入失败不会把半文件替换成目标文件。相同操作重试不得生成多次覆盖；已完成但回执丢失时，先依据操作记录和实际状态恢复，不能确认则标失败/待核验，不盲目重放。

### 5.3 删除与改名

- 只有明确的本地删除、可信原基线、另一端未修改且允许安全应用时才传播删除。
- 源设备离线、权限错误、目录扫描失败、范围排除变化不能产生删除指令。
- 正常删除不保留文件副本或另建回收站，但保留30天删除记录。删除后不能承诺从日志恢复原内容。
- 改名沿用“旧路径删除、新路径新增”，不新增复杂的改名推断；目标新路径已有不同变更时进入冲突。

## 6. 双方修改与冲突副本

### 6.1 双方都修改、文件均存在

1. 只对该文件读取双方内容并计算哈希，读取前后检查文件稳定。
2. 哈希相同：无需传输、无需冲突副本，更新双方各自的元数据基线；可记一次“双方变化但内容一致”的成功确认。
3. 哈希不同：当前文件各自保持原样，保存双方对应版本的冲突内容和来源，停止该路径自动覆盖。其他无冲突路径继续同步。

若文件在哈希核对中继续修改，不依据旧结果做决定；等待稳定后重试。冲突是同路径的实际内容分歧，**不是Git分支名称不一样**。

### 6.2 删除/修改冲突

一端已删除、另一端有修改时，保留尚存内容和双方存在状态。已删除的一端没有字节可备份，不伪造“删除前原件”；保留删除事实即可。只有用户明确解决冲突后，才传播最终选择。

### 6.3 保存和清理

- 冲突副本放在平台受控、不会被普通同步再次扫描的冲突存储区；界面展示原路径、设备、时间、大小、哈希（有时）和冲突ID。
- 保存必须确认完整；空间不足或复制失败时显示失败，保留双方当前文件，不自动覆盖。
- 同一冲突/同一版本不重复保存；双方又产生新版本时关联到同一文件的后续冲突，不丢已有待处理内容。
- 未解决冲突的副本不受“日志30天”清理影响。
- 建议默认：用户明确解决冲突、最终版本已成功应用到双方且没有未完成引用后，清理该冲突副本。不是新增永久版本库；具体清理边界随本稿审阅确认。
- 不自动调用模型改代码，也不自动选时间更晚的一方作为正确内容。

## 7. 同步记录

### 7.1 粒度与字段

每次实际文件同步尝试对应一条记录；同一条记录按关键阶段更新。失败重试生成新尝试，关联原操作，不抹掉先前失败。

| 字段 | 页面说明 |
| --- | --- |
| recordId / operationId / attempt | 记录、操作和尝试身份 |
| project / scope / relativePath | 哪个项目、仓库或共享范围的文件 |
| sourceDevice → targetDevice | 从哪台设备到哪台设备 |
| action | 新增、修改、删除、双端一致确认 |
| startedAt / finishedAt | 平台记录的开始、结束时间 |
| sourceBefore | 本次读取源文件的存在状态、修改时间、大小 |
| targetBefore | 覆盖/删除前目标属性，或“原来不存在” |
| targetAfter | 目标端完成后的实际属性；失败未完成则明确为空/未确认 |
| status | 同步中、成功、失败 |
| phase / reason | 等待设备、安全应用、传输、写入、冲突、超限等具体原因 |
| sourceHash / targetHash | 仅双端修改确实核算时填入；平时显示“未计算”，不得补造 |
| conflictId / retryOf | 冲突或上次失败记录的关联（如有） |
| transferredBytes / duration | 实际传输量与耗时，便于排查 |

文件版本在普通记录中以“修改时间＋大小”展示；操作编号用于顺序定位，不冒称Git SHA。设备时钟可能不同，日志按Home接收/确认时间排序，原文件时间作为数据展示。

### 7.2 状态含义

- **同步中**：已登记，正在等待设备/安全应用、传输或确认，附具体阶段；不能在实际未开始传输时误写正在上传。
- **成功**：目标完成应用并确认，或双方修改后核验哈希相同。依据不同要分别说明。
- **失败**：传输/写入失败、内容冲突、权限/范围问题、取消等导致本次未完成；保留原因和实际已完成部分，不当成已回滚。

状态不新增到聊天任务/Run状态中，不把CLI成功退出当成同步成功。不记录无变化扫描，不写每个传输分块的日志。

### 7.3 30天自动清理

- 以Home时间计算连续30×24小时。成功/失败记录从 `finishedAt` 算，超过30天自动删除。
- 每天至少执行一次有界清理；停机后恢复时补清理，分批执行，不全表加载、不长时间阻塞数据库。
- 长期未结束的同步中审计记录，以最近一次实际阶段变化时间计30天，过期也删除该审计行；不能靠无实质变化的刷新延长保留。操作仍由独立运行状态保存，不因日志删除而取消；之后真实进入新阶段或结束时，按原operationId生成新审计行，终态行从结束时间计30天。必要恢复信息不得只存于会被清理的审计行。
- 自动清理不删除业务文件、聊天历史、任务/Run、必要基线、未解决冲突内容、仍被引用的操作状态或当前配置。
- 超过30天的终态记录不可再查询；本需求不增加长期归档或自动导出。
- 已有系统旧副本/运行存储的一次性处理需单独列清单，不借日志清理批量删除历史数据。新策略只确保新产生的正常同步不长期保留旧文件副本。

### 7.4 页面入口

在现有项目“同步”相关页面/设置入口增加“同步记录”，不重排群聊界面，不另建全局任务页。

默认显示最近记录，每页50条；可按文件路径、设备、时间范围、状态筛选。点击看同步前后属性、失败原因、重试链和冲突入口。仅当前项目可见；首次加载不读取全部日志或文件正文，不要求用户常驻打开页面。

## 8. 正常副本、暂存和其他数据的区分

| 数据 | 是否保留 |
| --- | --- |
| 两端正在使用的文件 | 保留，它们是工作文件，不是历史备份 |
| 正常覆盖前的旧目标字节 | 不新增长期副本 |
| 正常删除前的文件字节 | 不新增副本，删除不可依靠日志恢复 |
| 新内容传输暂存 | 仅未完成操作需要时保留，确认结束且无引用后清理 |
| 双方内容冲突的版本 | 保留到冲突明确解决且双方应用确认 |
| 每文件当前同步基线 | 持续保留必要小量状态，不随30天日志消失 |
| 已结束同步审计记录 | 30天 |
| 原有Git提交、聊天附件、原生会话历史 | 本轮不改保留策略，也不删除 |

这不是文件备份产品。正常覆盖后发现修改错误，需要依靠用户原有Git或其他备份恢复；仅凭时间、大小和日志无法重建旧字节。

## 9. 资源和能力取舍

- 常态只读文件属性，不读取文件正文计算内容哈希。传输文件时当然仍需读取其字节，但不为日志再读第二遍。
- 只有双端修改文件计算哈希；重复同一稳定冲突可复用已知计算结果，文件属性改变后不得复用。
- 监听为主、元数据兜底为辅，保留现有扫描/传输并发限制、忙碌让路和失败退避。日志按文件和关键阶段写入，列表分页。
- 不新增CPU/内存高频轮询，不降低权限、不停止任务，不关同步。
- **接受的准确性限制**：内容被改变但mtime与大小均被刻意或通过工具保留时，简单模式可能漏检。取消周期性内容哈希后，不能保证自动发现此类变化；需要时另行明确执行内容核对，不能宣称本方案达到逐字节持续一致。
- **接受的额外传输**：原样保存但mtime改变，单端变化也会重传；这是避免每次读取计算哈希的取舍。
- 托管任务依赖既有占用门槛保护。外部程序不受平台调度约束，不能承诺对任意编辑器的并发写入具有全局文件锁；发现变化时停止覆盖并重判。

## 10. 接入现有实现的要求

当前同步实现广泛使用内容哈希、内容存储和共同基线，因此本功能**不是只替换一个比较条件**。实施计划应核实并复用既有模块，但必须覆盖以下衔接：

1. Worker观察：事件与元数据判定，简单模式取消周期性完整哈希，保留旧模式和能力协商。
2. Home判定：保存两端各自的确认属性，识别单端/双端变化，不以时间大小跨机排序。
3. 传输/应用：普通同步不强制预生成哈希Blob，不长期保留旧字节；仍使用稳定读取、短期暂存、目标重查和完成回执。
4. 冲突：双端修改才按需哈希并保存冲突版本，复用已有冲突入口。
5. 审计/清理：新增逐文件可查询记录，30天清理与操作恢复、基线、冲突存储解耦。
6. 页面：日志列表和明确的同步状态，不扩展为自动派工体系。

新旧Home/Worker必须明确识别模式；旧Worker不支持时显示需升级，不静默忽略策略。首次迁移先核活动任务和可信基线，保留用户源文件及现有历史，不直接操作数据库伪造成功。

本轮文档不会自动启用、迁移或部署。实施前提交按模块与验收分批的计划；最后独立审核、隔离双端实际验证，是否发布和真实项目启用另按用户授权。

## 11. 验收标准

| 编号 | 场景 | 必须结果 |
| --- | --- | --- |
| S01 | 两端属性未变化，收到重复事件或页面刷新 | 不读正文、不计算哈希、不传输、不增加日志 |
| S02 | 仅A修改、B未变 | 自动A→B，正确记录前后属性；不保留旧B副本 |
| S03 | 仅B修改、A未变 | 自动B→A；完成后无反复往返同步 |
| S04 | 单端原样保存但mtime变化 | 允许重传，不为判同额外计算内容哈希 |
| S05 | 双端修改但内容相同 | 仅该文件核对哈希，更新基线，不传输或留冲突副本 |
| S06 | 双端修改且内容不同 | 双方原件保留，冲突副本和原因可查；其他文件继续 |
| S07 | 传输期间源或目标又变化 | 不将不稳定/过时内容覆盖目标，不误记成功 |
| S08 | 目标有托管活动任务 | 等待安全应用，不中断或覆盖运行输入 |
| S09 | 正常单端删除；删除对修改 | 前者按规则同步删除不留备份；后者保留尚存内容并报冲突 |
| S10 | 断网、扫描失败、权限失败、排除项变化 | 不误判删除；显示具体失败/等待原因 |
| S11 | 初次两端都有文件但基线未知 | 默认不覆盖；用户明确选择覆盖初始化时先按疑似冲突保全双方，失败不覆盖；确认基线后清理无引用副本 |
| S12 | 接收端修改时间与来源不同 | 分别保存实际属性；无无限回传 |
| S13 | 中断、重启、丢失确认、重复请求 | 可恢复原操作，无重复覆盖；不确定状态不伪造成功 |
| S14 | 日志超过30天 | 终态记录自动清理；基线、业务文件、活动操作和未解决冲突不丢 |
| S15 | 冲突处理完成且双方已确认 | 正常恢复同步，按规则清理无引用冲突副本 |
| S16 | 文件属性相同但内容被工具替换 | 如实记录为已知漏检边界，不宣称能够自动发现 |
| S17 | 项目/设备/文件/状态过滤和分页 | 能定位具体尝试、前后属性、重试链；不全量加载 |
| S18 | 旧Worker或未迁移项目 | 保持旧行为或明确不支持，不暗中改策略 |
| S19 | 常态无变化10分钟及批量实际变更 | 记录CPU、RSS、扫描数、哈希次数、传输量和数据库增长；常态内容哈希次数为0 |
| S20 | 新增真实测试文档和图片跨Mac/Linux传输 | 两端实际可读；普通日志准确；未在业务项目中造测试任务或改原文件 |

验证采用隔离项目与虚构数据，并覆盖真实Mac/Linux Worker和浏览器。测试脚本、截图、私人设备路径和数据留在忽略目录，不进入公开仓库。代码通过、功能验证通过、已合并、已部署分别报告；不能用日志存在证明文件已正确同步。

## 12. 本稿需要一起审阅的明确取舍

- 不按两台设备谁的时间更晚决定胜负，而是对比双方各自的上次成功记录。
- 遵从“仅双端变化核对哈希”，不保留周期性完整内容哈希兜底，接受时间与大小被保留时可能漏检。
- 正常覆盖和删除没有历史字节备份；30天日志只用于反查，不能恢复文件。
- 30天约束针对审计记录，不删除必要基线、未完成操作或未解决冲突文件。
- 无可信首次基线不自动覆盖；明确选择覆盖初始化时按疑似分歧先保全双方。冲突/初始化明确解决后双方应用成功才清理无引用副本。
